# ShadowFlow 后端引擎（MVP）

截图里 ① 号位（后端：引擎 · 知识库 · 多智能体协作）的可运行初步产品。目标就四句话：

1. **Loop 引擎与 DAG 编排跑稳跑通** —— 循环是一等公民节点，逐轮写证据链，能急停、能断点续跑。
2. **知识库 RAG 补齐配置与检索链路** —— 词条入库、分块、混合检索、引用回传，`LIGHTRAG_ENABLED` 开关与能力盘点口径一致。
3. **多智能体协作稳定输出，为前端演示供好接口** —— 每一步都是一个带 seq 的事件，前端订阅 SSE 即可复刻全过程，不需要读引擎内部。
4. **交易闭环：扫码 → 付款 → 自动交付** —— 买家扫码提需求并付款，付款回调直接建工单交给 Agent 团队，跑完原地交付，全过程留痕。

> 前三条是 PPT 承诺，第四条是队友分工新增。两者的关系不是并列功能，而是一条链：
> `扫码下单 → 付款建单 → 团队执行 → 交付回传`，前三条能力跑在第三段里。

## 快速开始

**只想看效果，三步：**

1. 双击 `start.bat`（Windows）或执行 `sh start.sh`（mac/Linux）
2. 等出现 `Uvicorn running on http://127.0.0.1:8787`
3. 浏览器打开 <http://127.0.0.1:8787/?autorun=1> —— 会自动跑一次完整任务，约 8 秒

需要 Python 3.9+。脚本会自动装依赖，只装 `fastapi` 和 `uvicorn` 两个包。

手动方式：

```bash
cd shadowflow-backend
python -m pip install -r requirements.txt
python run.py                 # http://127.0.0.1:8787
```

打开 <http://127.0.0.1:8787> 就是演示控制台；想一进来直接起一次完整运行，用 `?autorun=1`。

想看买家侧（扫码下单），打开 <http://127.0.0.1:8787/shop>。要让手机真的扫得动，用
`SF_HOST=0.0.0.0 python run.py` 启动，并保证手机与电脑在同一个 WiFi —— 二维码里的地址会自动取局域网 IP。

默认**不依赖任何外部服务**：没配模型 Key 时走确定性模拟器，链路、事件、证据链与真实模型完全一致，方便反复彩排。
第一次启动会自动建 `data/shadowflow.db` 并写入种子数据（演示团队 + 10 条词条），删掉 `data/` 即可回到初始状态。

接入真实模型（OpenAI 兼容）：

```bash
export SF_LLM_BASE_URL=https://api.xxx.com/v1
export SF_LLM_API_KEY=sk-...
export SF_LLM_MODEL=gpt-4o-mini
python run.py
```

| 环境变量 | 默认 | 说明 |
| --- | --- | --- |
| `SF_PORT` | 8787 | 服务端口 |
| `SF_HOST` | 127.0.0.1 | 设 `0.0.0.0` 后手机才能扫码打开（同一 WiFi） |
| `SF_PAY_MODE` | simulated | 支付网关：`simulated` / `wechat` / `alipay` |
| `SF_PUBLIC_BASE_URL` | 空 | 二维码里写的对外地址；留空时自动用局域网 IP |
| `LIGHTRAG_ENABLED` | 1 | 设 0 时检索链路旁路返回 stub（复刻 P10 口径） |
| `SF_KB_TOP_K` | 4 | 每轮检索条数 |
| `SF_LOOP_MAX_DEPTH` | 4 | 循环嵌套上限 |
| `SF_MAX_ROLLBACKS` | 2 | 单次运行的驳回回滚上限 |
| `SF_STEP_DELAY` | 0.35 | 每步停留秒数，只为让演示看得清；设 0 关掉 |
| `SF_DATA_DIR` | ./data | SQLite 与运行数据目录 |

## 一次运行会发生什么

默认团队「OPC 出海增长小组」：`情报侦察 → 策略定盘 → 内容打磨闭环(loop) → 合规审核 → 交付汇总`。

实际跑出来的时间线（43 条事件，可直接对照控制台）：

```
1  起跑          任务入队，记录 llm/kb 模式
2  派发 情报侦察
3  汇报 情报侦察   （带 3 条 KB 引用）
...
8  循环 内容打磨闭环  最多 4 轮 / 阈值 0.85
10 初稿 0.60 → 未达标，继续
15 二稿 0.75 → 未达标，继续
20 定稿 0.90 → 达标，收敛退出        每轮写一条 IterationRecord + 一个 checkpoint
26 合规审核 REJECT（风险 + 必须修改项）
28 回滚至「内容打磨闭环」上一轮断点
31 内容撰写（携带法务意见）0.90 达标
37 合规审核 APPROVE
39 人工门：合规 → 交付需审批（演示环境自动放行）
41 交付汇总
43 完成
```

这就是"驳回不是报错，是流程"的可演示版本：被拒产出不落库，任务自动重排给上游，第二次一轮过。

## 交易链路：扫码 → 付款 → 自动交付

打开 <http://127.0.0.1:8787/shop> 是服务台，三个上架服务各带一个二维码。

```
买家手机扫码
   ↓  填一句话需求（必填）、称呼、联系方式（选填）
POST /api/orders            建单，返回支付凭据（沙箱里是一个付钱链接）
   ↓  点「确认支付」
POST /api/pay/notify        统一回调：验签 → 幂等 → 订单置 paid
   ↓  付款即开工，不等人工接单
POST /api/runs（内部）      需求直接成为本次 run 的任务描述
   ↓  Agent 团队按 DAG 执行，驳回回滚照常
GET /api/orders/{id}        买家页轮询，看到每个环节的真实状态
   ↓  run completed
订单置 delivered            附交付物 + 证据摘要（几轮审校、几个回溯点）
```

订单状态机（单向，除退款）：

```
created → pending_payment → paid → running → delivered
                                  ↘ failed
   未付款 → cancelled        已付款 → refunded（人工确认）
```

**支付是沙箱，这一点必须对使用者说清楚。** 真实收款需要商户号，而微信支付与支付宝的商户号都要求企业资质，个人申请不下来，也就没有可用的支付回调 —— 所以「扫码付钱、自动开工」在个人主体下做不到闭环。

本仓库的处理方式是**可切换网关**（`app/pay.py`），和模型层的模拟器同一套哲学：

| `SF_PAY_MODE` | 行为 |
| --- | --- |
| `simulated`（默认） | 本地沙箱，点确认即回调成功，**不扣真实款项**，演示可重复 |
| `wechat` | 需要 `SF_WECHAT_MCHID` / `SF_WECHAT_APPID` / `SF_WECHAT_API_KEY` |
| `alipay` | 需要 `SF_ALIPAY_APPID` / `SF_ALIPAY_PRIVATE_KEY` |

缺配置时**直接报 503，绝不静默降级成假成功** —— 演示时假成功比报错更危险。
回调路由 `/api/pay/notify`、幂等处理、订单状态机都已经按真实网关的形状写好，
将来补上商户号与签名验证即可切换，前端页面与引擎一行都不用改。

## OPC OS：把引擎变成一家公司

打开 <http://127.0.0.1:8787/api/os> 是管理台。默认已经开好一家公司：**增长工场 Growth Studio**，AI 增长营销赛道，5 个部门 9 名数字员工，启动资金 2000 元。

### 五层结构

```
老板（人）      目标制定 · 关键审批 · 经营决策
   ↓
公司层          组织架构 · 员工名册 · 审批流 · 经营账本     ← 本次新增
   ↓
任务层          项目 · 任务协议 · 交接 · 成本归集            ← 本次新增
   ↓
执行层          DAG · Loop · 策略矩阵 · 知识库 · 模型        ← 已有
   ↓
交付层          订单 · 交付物 · 收款                          ← 已有
```

前两层是这次补的，后两层是前几轮已经跑通的。**新增的层不碰模型调用细节，只决定「谁、在什么授权下、做什么、花多少钱」。**

### 员工不是一段 prompt

九个员工各自带岗位、部门、技能、权限、模型、日成本、绩效和状态：

| 员工 | 岗位 | 部门 | 模型 |
| --- | --- | --- | --- |
| 陈明远 | CEO 助理 · 项目经理 | 总经办 | Claude Sonnet |
| 苏策 | 品牌策划师 | 品牌策略部 | Claude Sonnet |
| 陆审 | 质量审核 | 品牌策略部 | Claude Sonnet |
| 罗法 | 合规审核 | 品牌策略部 | Qwen Max |
| 林研 | 市场研究员 | 市场研究部 | GPT-4o |
| 周数 | 数据分析师 | 市场研究部 | DeepSeek V3 |
| 何文 | 文案运营 | 创意制作部 | DeepSeek V3 |
| 江设 | 视觉设计师 | 创意制作部 | Gemini Flash |
| 沈客 | 客户经理 | 客户成功部 | GPT-4o |

五种模型跑在同一个框架里，按岗位分工：需要判断力和文风的岗位用旗舰模型，批量化、结构化的岗位用性价比模型。模型单价写进 `MODEL_CATALOG`，每个任务的成本可以逐笔核算。

### 任务协议：一个任务必须能追到五件事

`app/company.py` 里的任务不是待办事项，是一份契约：

| 要素 | 落在哪 | 用途 |
| --- | --- | --- |
| 责任人 | `assignee_employee_id` | 谁做的，可追到员工卡片 |
| 执行过程 | `run_id` + 事件流 | 每一轮怎么想的、改了什么 |
| 交接记录 | `handoff_json` | 上下游交付了什么，不用重读全库 |
| 成本 | `cost_cents` + `ledger` | 模型费 + 工时分摊，进账本 |
| 交付结果 | `output_json` | 正文、摘要、引用、tokens |

### 风险分级：哪些决策必须人来做

| 风险 | 谁来批 | 例子 |
| --- | --- | --- |
| `low` | 自动放行 | 内部调研、分析、文案初稿 |
| `medium` | 老板在管理台点通过 | 对外物料（视觉、投放素材） |
| `high` | 老板本人，不可跳过 | 合规审查、对外发布 |

演示时最能说明问题的一幕：项目跑到「视觉物料设计」会**停下来等你**，一路「继续执行」推到「合规审查」又停下一次。这两次停顿就是「哪些决策需要人」的答案。

> 客户已付款的订单走另一条规则：审批照常生成、照常留痕，但由系统代老板放行，
> 避免客户卡在公司内部流程上。这个取舍在 `orders._execute_project` 里，一眼可见。

### 经营数据是真的

每一个任务执行完都会写一条账本流水：模型调用成本（按 tokens × 单价）加上工时分摊（日成本 ÷ 8）。订单交付时自动记一笔收入。所以首页那四个数字不是装饰：

```
营收 ¥499　成本 ¥79　毛利 ¥420　毛利率 84.2%
```

这个成本结构就是「一人公司」的账：人力成本几乎为零，主要成本是模型调用与极少量工时。

### 和交易链路是接上的

客户扫码下单付款之后，**那一单直接变成公司的一个项目**，走组织、走任务依赖、走审批，而不是另起一套流程：

```
扫码付款 → 建项目 → 按剧本拆成 9 个任务 → 并行执行
       → 两次审批（系统代批，留痕） → 项目 delivered
       → 订单 delivered + 自动记收入 → 客户端看到交付物
```

## 四个演示动作

**A. 主线（约 8 秒）**：控制台点「开始执行」。看 DAG 节点颜色流转、右侧逐轮得分 0.60 → 0.75 → 0.90、事件流里法务驳回与回滚。

**B. 急停 + 断点续跑**：跑起来后点「急停」，状态变 stopped，checkpoint 已落库；点「断点续跑」，从最近断点接着跑完，已完成的节点会打 `node.skipped`。

```bash
curl -X POST http://127.0.0.1:8787/api/runs/<id>/stop
curl -X POST http://127.0.0.1:8787/api/runs/<id>/resume
```

**C. 策略矩阵拦截**：左侧选「内容撰写 → 合规审核」，点「查表判定」，返回 `deny`；点「编译期校验」，任意塞一个 `writer → legal` 的直连团队，会拿到四眼原则错误并拒绝保存。

**D. 扫码下单全链路（约 30 秒）**：打开 `/shop`，手机扫「出海选品作战包」的二维码 → 填一句话需求 → 点支付 → 确认 → 停在进度页看团队逐环节亮起 → 约 10 秒后原地出现交付物。

```bash
# 命令行也能走完同一条链
curl -X POST http://127.0.0.1:8787/api/orders -H "Content-Type: application/json" \
  -d '{"product_id":"svc_landing_sel","requirement":"东南亚轻小件怎么选品，7天跑通首单"}'
# 拿返回里的 order.id 和 payment.txn_id，再回调：
curl -X POST http://127.0.0.1:8787/api/pay/notify -H "Content-Type: application/json" \
  -d '{"provider":"simulated","order_id":"<ord_id>","txn_id":"<txn>"}'
```

## 与能力盘点的差距（如实标注）

| 项 | 状态 |
| --- | --- |
| Loop 引擎 / 策略矩阵 / 驳回回滚 | 本仓库可跑，事件与证据链可逐个核对 |
| 知识库 RAG | 可用的本地混合检索（分块 + 向量 + BM25）；能查、能增，**不能删、不能传文件**；换 LIGHTRAG 服务只需替换 `kb.search` |
| 真实 LLM | 已留 OpenAI 兼容通道，配 Key 即切；未配时走模拟器 |
| 交易闭合 | 下单 → 支付回调 → 建工单 → 交付 → 留痕，全链路可跑；**收款是沙箱，真实扣款未接**（无商户号） |
| 退款 | 只有状态位 `refunded`，未接真实退款接口，也没有对账 |
| OPC 公司层 | 组织、员工、项目、任务协议、审批、账本全部可跑，数据落在 SQLite |
| 任务级并行 | 任务层按依赖图并行（同一层最多 3 个同时跑）；**旧版 run 的 DAG 仍是串行** |
| 跨任务长期记忆 | **未做**。员工记得自己的技能与历史绩效，但不记得上一次项目学过什么 |
| 多公司 | 数据模型支持，界面只展示第一家公司 |
| 公司知识库隔离 | 知识库是全局的，尚未按公司/部门分库 |
| 定时任务 | 未实现，只有运行期调度 |
| AgentTeams 集群版（K8s + Matrix 桥） | 不在本 MVP，需要集群联调 |
| 记忆系统 | 用 checkpoint 承担跨轮/跨断点的状态沉淀，**未做独立的跨任务长期记忆** |

## 已知限制

- 事件流用 150ms 轮询 SQLite 落库（而非内存队列），牺牲一点实时性换取"断线可重放、重启不丢"。真上量时应换 Redis Stream / Kafka，接口保持 `seq` 语义不变。
- 旧版 run 按拓扑序串行执行；任务层已支持依赖图并行，两套执行器并存。
- SQLite 单写锁，适合演示与小队内部使用，不适合多租户并发。
- 买家页靠轮询刷新（1.5s），不是推送；订单多了应换成 SSE 或 WebSocket。
- 订单交付物取「内容撰写」角色最后一次产出 + 交付汇总；多产出物的打包下载未做。
