## 1. 引言:为什么是现在

2024 年底以来,LLM 应用从「单 agent + 工具」快速走向「多 agent 协作」。驱动力有三:

1. **上下文窗口的物理上限**:再大的窗口也装不下一个真实研究/工程任务的全部材料。把任务拆给多个各自独立上下文的 subagent,是绕开「context rot」的工程手段。
2. **并行带来的吞吐**:研究、检索、代码审查这类任务天然可并行,多 agent 把墙钟时间从「串行求和」压到「最慢单链」。
3. **协议元年**:2024-11 Anthropic 发布 **MCP**,2025-03 IBM 发布 **ACP**,2025-04 Google 发布 **A2A**——一年之内,agent 与工具、agent 与 agent 的互通从「各家私有」走向「开放标准 + 中立治理(Linux Foundation)」。这被普遍类比为 agent 领域的 "LSP 时刻"。

但 2025 年也出现了强烈的反向声音:**Cognition「Don't Build Multi-Agents」**、以及 Berkeley **MAST** 实证研究指出多 agent 系统在多数基准上相对单 agent 的提升「往往微乎其微」。多 agent 不是银弹——**何时该用、用哪种拓扑、怎么通信**,才是这篇调研要回答的。

## 2. 协作范式(Collaboration Paradigms)

多 agent 系统的「形状」由 **编排拓扑** 决定。下面是当前主流的几类,按「中心化程度」从高到低大致排列。

### 2.1 编排拓扑一览

| 拓扑 | 机制 | 适用场景 | 代表实现 | 主要缺点 |
|---|---|---|---|---|
| **Orchestrator-Worker**(主从/编排器) | 一个 lead agent 拆解任务、分派给 worker subagent、汇总 | 研究、深检索、可并行子任务 | Anthropic 研究系统、AutoGen `MagenticOneGroupChat`、OpenAI Agents SDK | lead 是瓶颈 + 单点;token 爆炸 |
| **Sequential / Pipeline**(流水线) | agent 按固定顺序串联,前者产出喂后者 | SOP 明确的流程(需求→设计→编码→测试) | MetaGPT、CrewAI(sequential) | 无并行;错误沿链传播 |
| **Hierarchical**(层级) | 多层 manager-worker 树,逐层分解 | 大型复杂任务、组织化分工 | CrewAI(hierarchical)、AutoGen 嵌套 team | 层级越深越难调试 |
| **Graph / State Machine**(DAG/状态机) | 节点=agent,边=控制流;显式声明依赖与分支 | 需要确定性控制流、可视化、可恢复 | LangGraph、ShadowFlow chat-DAG | 表达力换来配置复杂度 |
| **Group Chat / Blackboard**(群聊/黑板) | 共享会话/黑板,多 agent 轮流读写,由 selector 决定下一个发言者 | 协作讨论、动态分工 | AutoGen `SelectorGroupChat`/`RoundRobinGroupChat` | 上下文膨胀;发言权裁决难 |
| **Debate**(辩论) | 多 agent 对同一问题独立作答→互相批驳→收敛 | 推理、事实核查、降低幻觉 | Multi-Agent Debate、Society of Mind | 成本高;可能「群体顺从」 |
| **Market / Auction**(市场/拍卖) | agent 对子任务竞价,按能力/成本分配 | 去中心化资源分配、异构 agent 市场 | 偏研究;A2A 的跨厂商发现是基础设施雏形 | 工程落地少;协议依赖强 |
| **Swarm / Handoff**(蜂群/移交) | 无中心,agent 间通过「移交(handoff)」转移控制权 | 客服/分诊式路由、轻量协作 | OpenAI Swarm → Agents SDK | 全局状态难追踪 |

### 2.2 中心化 vs 去中心化

- **中心化(orchestrator)**:控制流清晰、易做全局规划与终止判断,但 lead agent 是单点 + token 瓶颈,且容易「把 subagent 当函数调」而丢失协作的涌现价值。
- **去中心化(swarm/market/debate)**:鲁棒、可涌现,但全局一致性、终止条件、可观测性都更难。
- **2026 的工程共识**:绝大多数生产系统落在 **orchestrator + subagent** 这一保守中心化区间(Anthropic、OpenAI 均如此),把去中心化留给研究与特定场景。

> **判断锚点**:拓扑选择本质是在「**可控性**(中心化)」与「**鲁棒性/涌现**(去中心化)」之间取舍。任务越需要确定性产出与可恢复 → 越往 DAG/pipeline 走;越需要探索性与并行广度 → 越往 orchestrator-worker / debate 走。

## 3. 通信机制(Communication Mechanisms)

拓扑决定「谁跟谁连」,通信机制决定「连上之后怎么传信息」。

### 3.1 信息载体:共享内存 / 消息传递 / 事件总线 / 共享文档

- **共享内存 / 黑板(Shared Memory / Blackboard)**:所有 agent 读写同一块状态(会话历史、共享 scratchpad)。简单直接,但上下文随 agent 数线性膨胀,且「谁污染了状态」难追溯。AutoGen 的 GroupChat、多数「把对话历史全量塞进每个 agent」的实现属此类。
- **显式消息传递(Message Passing)**:agent 间发结构化消息,各自维护独立上下文。AutoGen v0.4 的 **actor 模型**是典型——agent 是可寻址实体,收发**带类型的异步消息**,支持 event-driven 与 request/response 两种模式。隔离性好,可扩展,但需要设计消息 schema。
- **事件总线 / Pub-Sub**:agent 订阅主题,产出以事件广播。适合一对多通知、流式 UI 推送(ShadowFlow 的群 SSE 总线即此类:按 group_id 分桶,agent 回复 publish 给该群所有订阅者)。
- **共享文件 / 文档(Filesystem / Document as Shared Memory)**:把「黑板」从易失内存**落到文件系统上一份持久、人可读、可 diff 的文档**(通常是 markdown)。它是黑板模式(1980s 经典 AI 架构,如 Hearsay-II)的现代化身,也叫 *artifact-based / document-centric coordination*。**独占优势**:持久(天然 checkpoint,抗重启)、人可读(协作介质同时是审计轨迹)、结构即治理(按 section 给每个 agent 划地盘 = 把 RACI/PolicyMatrix gate 落成"谁能改哪段")。**仍在的坑**(继承黑板):并发写冲突(需单写者或 section 分区所有权)、整份文档越长读它越贵(需分段 + 只读相关段 + 周期压缩)、md 与真实状态的真源漂移。代表实现:
  - **MetaGPT** —— 最纯正:角色间不闲聊,而是发布/订阅**结构化文档**(PRD→设计→代码→测试),文档即"消息"。
  - **Manus** —— 单 agent 用 `todo.md`,每步重写它把目标"复诵(recitation)"回最近上下文防跑偏。
  - **Anthropic 研究系统** —— subagent 把产出写到**外部 memory/文件**而非全塞回 orchestrator 上下文,绕开 15× token 的一部分。
  - **Claude Code / CCPM** —— `CLAUDE.md`、plan 文件、并行 agent 各自维护的 `stream-{X}.md` 进度文件(Completed / Working On / Blocked)互读协调。**ShadowFlow 仓库内 `.claude/rules/agent-coordination.md` 即明文采用此法**("Communication Between Agents → Through Progress Files"),是现成样板,只是尚未接进产品。

### 3.2 消息格式:结构化 vs 自然语言

- **自然语言**:灵活、人可读,但歧义大、易丢约束(Anthropic 发现 subagent 拿到模糊任务描述就会重复劳动/留缺口)。
- **结构化(JSON / 函数调用 / 带 schema 的产物)**:可校验、可路由、可程序化消费。趋势是 **「自然语言推理 + 结构化交接」**——agent 内部用 NL 思考,跨 agent 边界用结构化产物交接。

### 3.3 交接语义:Handoff

OpenAI 的 **Swarm**(及其继任 **Agents SDK**)把 agent 间协作抽象成 **handoff**:当前 agent 决定把控制权(连同上下文)移交给另一个更合适的 agent。相比「orchestrator 调用 worker 再收回」,handoff 是**控制权转移**而非**函数调用**,更适合分诊/路由式场景。

### 3.4 上下文工程与隔离(Context Engineering)

这是 2025 年最重要的通信议题。两种相反主张:

- **隔离派(Anthropic 多 agent)**:每个 subagent 独立上下文窗口,lead 只传「目标 + 输出格式 + 工具/来源指引 + 清晰边界」。好处是绕开单窗口上限、并行;代价是 token 爆炸与「跨 agent 上下文不一致」风险。
- **统一派(Cognition「Don't Build Multi-Agents」)**:主张**线性单线程 + 全程共享完整上下文**才可靠;多 agent 的脆弱性本质都是「**缺失上下文**」(agent 基于冲突假设/不完整信息行动)。其结论:**context engineering(动态、自动地把对的上下文喂给模型)是构建 agent 的第一要务**,优先于堆 agent 数量。

> 这条争论详见 §6,是当前领域最核心的分歧。

### 3.5 协议层:MCP / A2A / ACP

2025 是「agent 协议标准化」的关键年。三个协议**不是竞争而是分层**:

| 协议 | 提出方/时间 | 定位(分层) | 类比 |
|---|---|---|---|
| **MCP**(Model Context Protocol) | Anthropic · 2024-11 | **model ↔ tool**:让 LLM 挂载数据源/API/工具 | "USB-C 口" |
| **A2A**(Agent2Agent) | Google · 2025-04 | **agent ↔ agent**:跨厂商发现、能力交换、任务协作(公网互通) | "agent 的 HTTP" |
| **ACP**(Agent Communication Protocol) | IBM · 2025-03 | **agent ↔ agent**:纯 REST、无需专用 SDK,强调长任务持久态/异步/可靠性 | 企业级 REST 消息层 |

**2025 年的关键整合(务必记住,很多旧资料没跟上)**:

- **2025-06-23**:Google 把 **A2A 捐给 Linux Foundation**(中立治理);AWS、Cisco、微软、Salesforce、SAP、ServiceNow 等 100+ 公司加入。
- **2025-09**:IBM 宣布 **ACP 正式并入 A2A**(同在 Linux Foundation 下)。ACP 最具特色的可靠性能力(任务持久化、异步续跑、webhook 进度)已成为 **A2A v1.0** 的一部分。
- **结果**:**MCP(取工具)+ A2A(agent 互通)成为事实双栈**。BeeAI(原建于 ACP)现在的范式就是:**A2A 做 agent 间通信,单个 agent 内部用 MCP 取工具**。

> **对 ShadowFlow 的关系**:ShadowFlow 早在 2026-04 即拍板「**ACP 主 / MCP 辅**」的接入策略(见内部 `project_hermes_protocol_decision`)。鉴于上述 ACP→A2A 合流,接手者应把「ACP 主」理解为「A2A/ACP 谱系的 agent 互通层为主,MCP 取工具为辅」,并关注 A2A v1.0 是否值得跟进。

## 4. 智能体框架(Agent Frameworks)

> 用户特别要求展开本节。框架是上面范式/通信机制的工程封装。

### 4.1 主流框架对比

| 框架 | 出品 | 编排模型 | 通信/状态 | 适用场景 | 成熟度 |
|---|---|---|---|---|---|
| **LangGraph** | LangChain | **图(状态机/DAG)**,显式节点+边+共享 state | 共享 `State` 对象 + 检查点(可恢复/时间旅行) | 需要确定性控制流、分支、人审、可恢复的生产工作流 | 高,生产采用广 |
| **AutoGen v0.4** | Microsoft | **actor 模型** + 多种 GroupChat(RoundRobin/Selector/MagenticOne) | 类型化**异步消息**;`autogen-core`/`agentchat`/`ext` 三层 | 对话式多 agent、研究型协作、需扩展性/可观测(OpenTelemetry) | 高,v0.4 为重写版 |
| **Magentic-One** | Microsoft | orchestrator + 专用 agent(Web/File/Coder/Terminal) | 建于 AutoGen 之上 | 文件/网页类复杂任务的开箱 team | 中,偏参考实现 |
| **CrewAI** | CrewAI | **角色制 crew**:sequential / hierarchical 流程 | 任务上下文传递;role/goal/backstory | 快速搭「角色分工」团队,低门槛 | 高,社区大 |
| **OpenAI Agents SDK**(← Swarm) | OpenAI | **handoff** + tools + guardrails | 轻量;控制权移交 | 分诊/路由式、生产级轻量编排 | 高,官方主推 |
| **MetaGPT** | 开源 | **SOP 流水线**(模拟软件公司角色) | 结构化文档交接 | 代码生成、SOP 明确的协作 | 中,研究+实用 |
| **CAMEL** | 开源/研究 | **角色扮演**双/多 agent | 对话驱动 | 自动协作数据生成、社会模拟 | 中,研究导向 |
| **Claude Agent SDK** | Anthropic | subagent + 工具 + MCP | 独立上下文 subagent | 建于 Claude 的 orchestrator-worker | 上升中 |
| **Semantic Kernel** | Microsoft | planner + plugin;Agent Framework | 与 AutoGen 逐步融合 | 企业 .NET/Python 集成 | 高(企业) |
| **Google ADK**(Agent Development Kit) | Google | 与 A2A 配套的 agent 构建 | A2A 原生 | 跟 A2A 生态绑定的多 agent | 上升中 |

### 4.2 选型经验法则

- **要确定性控制流 / 可恢复 / 可视化** → **LangGraph**(图)或自建 DAG 执行器(如 ShadowFlow)。
- **要对话式协作 / 扩展性 / 可观测** → **AutoGen v0.4**(actor + GroupChat)。
- **要最快搭出「一个有角色分工的团队」** → **CrewAI**。
- **要生产级、轻量、官方支持、handoff 路由** → **OpenAI Agents SDK**。
- **要跨厂商 agent 互通** → 关注 **A2A + ADK / BeeAI**,而非绑死某个框架。
- **共性趋势**:框架都在收敛到「**图/状态机做编排骨架 + MCP 取工具 + A2A 做跨 agent**」,差异更多在 DX 与生态而非核心能力。

## 5. 先进论文与研究前沿

### 5.1 自动化工作流生成(Automated Workflow Generation)

手工设计多 agent 拓扑费时且次优,这条线让「**拓扑本身**」可被搜索/优化。

- **AFlow: Automating Agentic Workflow Generation**(arXiv **2410.10762**,**ICLR 2025 Oral**)。把 workflow 优化重构成**对「代码表示的 workflow」的搜索问题**(LLM 调用是节点,边是控制流),用 **蒙特卡洛树搜索(MCTS)** + 软混合概率选择 + LLM 驱动节点扩展 + 执行反馈回传,自动探索 workflow 空间。6 个基准平均 **+5.7%**,并让小模型在特定任务上以 **GPT-4o 推理成本的 4.55%** 超过 GPT-4o。后续有 `A²Flow`(自适应抽象算子,arXiv 2511.20693)等延伸。
- 同一谱系:**ADAS**(Automated Design of Agentic Systems,用「meta agent」编程式搜索 agent 设计)、**GPTSwarm**(把 agent 系统建模为图并优化图结构)、**DyLAN**(动态分层 agent 网络,按任务动态选择 agent)、**EvoAgent**(进化算法生成 agent)。
- **意义**:这是「agent 系统从手工配置走向自动搜索」的方向,与 ShadowFlow 把 roster/拓扑做成确定性 Rule + 可校验 DAG 的思路互补(一个自动搜、一个确定性约束)。

### 5.2 角色分工与社会模拟

- **MetaGPT**:把软件公司 SOP 编码进多 agent,结构化文档在角色间流转,显著降低协作的「乱聊」开销。
- **CAMEL**(Communicative Agents):role-playing 双 agent,用于自动生成协作对话数据、研究 agent 社会行为。
- **Generative Agents**(斯坦福「AI 小镇」):25 个生成式 agent 在沙盒中产生可信的个体与涌现群体行为,是「记忆-反思-规划」架构的范式样本。

### 5.3 辩论与自我改进

- **Multi-Agent Debate**:多 agent 独立作答后互相批驳,在推理/事实任务上降幻觉、提准确率。
- **Society of Mind**(Minsky 思想的 LLM 落地):多个简单 agent 的交互涌现出复杂智能。
- **Reflexion**:agent 用语言化的自我反思作为「记忆」改进后续尝试(单 agent 自改进,但常被并入多 agent 的 verifier 角色)。

### 5.4 失败模式与评估(这是给工程团队的「冷水」)

- **MAST: Why Do Multi-Agent LLM Systems Fail?**(arXiv **2503.13657**,**NeurIPS 2025**,UC Berkeley Sky Computing Lab)。**第一个实证的多 agent 失败分类法**:分析 7 个主流 MAS 框架、200+ 任务、6 名专家标注,得 **14 种失败模式**,归为 3 大类:
  1. **Specification & System Design(规格与系统设计)— 42%**:agent 忽略任务指令、越权、无进展地重复步骤、丢失上下文、识别不出任务已完成。
  2. **Inter-Agent Misalignment(agent 间错位)— 37%**:误差跨 agent 累积、任务分解差、沟通断裂。
  3. **Task Verification & Termination(验证与终止)— 21%**:输出校验/质量门不足。
  - 方法严谨:Cohen's Kappa **0.88**,配套 **MAST-Data** 1600+ 标注 trace。
  - **核心结论**:多 agent 在主流基准上相对单 agent 的提升常常很小,**多数失败源于系统设计而非模型能力**——agent 带着错误假设运行、忽略同伴输入、不验证自己的产出。

> **给 ShadowFlow 的直接启示**:MAST 的 42% 来自「规格/设计」——这正是 ShadowFlow 押注的「**确定性 Rule + 写时 DAG 校验 + PolicyMatrix gate + validation hooks**」想消灭的失败类别。把这套校验做扎实,理论上能砍掉接近一半的多 agent 失败。

## 6. 关键争论:要不要上多 agent?

2025 年最具代表性的两极:

**Anthropic(支持,有条件)** — 在《How we built our multi-agent research system》中给出可量化结论:

- orchestrator-worker 架构,lead 拆解任务并给每个 subagent「目标 + 输出格式 + 工具/来源指引 + 清晰边界」。
- **成本**:agent 约用 **4×** 普通 chat 的 token,多 agent 约 **15×**。**token 用量本身解释了 BrowseComp 上 80% 的性能方差**(另两因子是工具调用次数与模型选择)。
- **收益**:在内部研究评测上**比单 agent Claude Opus 4 高 90.2%**。
- **适用边界(明确写出)**:多 agent 只在「**重并行 + 信息超单窗口 + 大量复杂工具**」且「**任务价值高到能付得起 15× token**」时才划算。

**Cognition(反对,默认不要)** — 《Don't Build Multi-Agents》:

- 2025 年「多 agent 协作」只会得到**脆弱**系统,可靠性的核心是 **context engineering**。
- 失败几乎总能归因到「**缺失上下文**」:agent 基于冲突假设/不完整信息行动。
- 对**编码**这类「依赖紧、上下文共享关键」的任务,**线性单线程**更合适。

**2026 的折中共识**:不是「要不要多 agent」,而是「**哪种任务用多 agent**」。决策清单:

| 该上多 agent ✅ | 该用单 agent / 长上下文 ❌ |
|---|---|
| 任务可重并行(检索、广覆盖研究) | 子任务依赖紧、需共享完整上下文(编码) |
| 信息量超单个上下文窗口 | 上下文能装进一个窗口 |
| 需要多个独立视角/对抗验证 | 需要强一致、确定性产出 |
| 任务价值高,付得起 ~15× token | 成本敏感、低价值任务 |
| 接口大量异构复杂工具 | 工具少、流程线性 |

## 7. 工程挑战(落地必踩)

1. **上下文一致性**:跨 agent 的假设/事实不一致是头号失败源(MAST 37% + Cognition 论点)。对策:结构化交接、共享只读事实库、显式传「任务边界」。
2. **错误传播 / 级联**:pipeline/层级里前序错误被后续放大。对策:每节点验证关卡(verifier)、policy gate、重试预算。
3. **成本(token 爆炸)**:多 agent ~15× token。对策:按任务价值门控是否上多 agent、限制 fan-out 数、缓存与上下文裁剪。
4. **可观测性 / 调试**:并发 + 非确定性使复现极难。对策:run 级事件日志(单调 id、可重放)、OpenTelemetry span、trace 标注(MAST 即靠人标 trace)。
5. **评估难**:多 agent 产出开放、过程长,end-state 评分 + LLM-judge + 人审三者结合。
6. **确定性 vs 涌现**:越确定越可控但越死板,越涌现越强但越难保证。主流做法是「**确定性骨架(DAG/状态机)承载控制流 + 在节点内留 LLM 自主**」。
7. **终止判断**:agent 识别不出「任务已完成」是 MAST 明列的失败模式;需要显式终止条件而非靠模型自觉。

## 8. 趋势与展望

1. **协议标准化收口**:MCP(工具)+ A2A(agent 互通,已吸收 ACP)成事实双栈,均在 Linux Foundation 中立治理下。跨厂商 agent 互操作从愿景变基础设施。
2. **agent 市场 / 互操作**:A2A 的「跨厂商发现」是 agent 市场的协议雏形,未来可能出现按能力/成本的 agent 撮合。
3. **自动化编排生成**:AFlow/ADAS/GPTSwarm 这条线,让「拓扑/workflow」从手工配置走向可搜索可优化。
4. **确定性 workflow 与自主 agent 融合**:LangGraph(图)、确定性 DAG + 节点内自主,是当前最被生产采纳的折中,预计继续主流化。
5. **可靠性工程上位**:MAST 这类实证研究把焦点从「能不能做」转向「为什么失败 + 怎么不失败」,验证/校验/上下文工程成为一等公民。

## 9. 对 ShadowFlow 的启示

把上面的范式/协议/框架映射回 ShadowFlow(详见同目录交接文档),对得上的点:

| 领域共识 / 前沿 | ShadowFlow 的对应物 | 评价 / 可借鉴 |
|---|---|---|
| Orchestrator-worker / DAG 编排 | chat-DAG 执行器(分层并发 + gate + 超时/重试/取消) | 方向正确;缺中断恢复、conditional rework(对标 LangGraph 检查点) |
| MCP 取工具 + A2A agent 互通 | ACP 主 / MCP 辅 + `acp_server.py` / `a2a_bridge.py` | 应跟进 ACP→A2A 合流,评估 A2A v1.0 |
| 上下文工程(Cognition) | 串行 fan-out 每轮重读历史 + DAG 上游产出经 gate 过滤注入 | 已有「按边传上游」雏形;可加结构化交接 schema |
| **共享文件/文档(Filesystem as shared memory)** | 群级 `workspace_dir`(CLI 工作目录)+ 设计中的**河流式记忆系统**(主流/支流/沉淀 + drink/pour/settle) | 河流记忆概念上**就是**一个共享协作基底;落地最小切口=群 `workspace_dir` 里放一份分 section 的 `shared.md`,DAG 节点 `drink` 它当上游、`pour` 产出回去,把"参数传递上游"升级成"经持久文档传递"。所有权按 section 映射 RACI/PolicyMatrix gate。先例:MetaGPT / 仓库内 `stream-{X}.md` |
| MAST 42% 规格/设计失败 | 确定性 roster Rule + 写时 DAG 校验(422)+ PolicyMatrix gate + validation hooks | **这是 ShadowFlow 最对的赌注**;做扎实可砍近半失败 |
| MAST 21% 验证/终止失败 | validation_hooks(N1/002)+ policy warn 交「拍板/审核点」 | 终止条件仍偏弱,可显式化 |
| AFlow 自动 workflow 生成 | 当前是「确定性约束 + 人配 DAG」 | 互补方向;远期可引入搜索式拓扑生成 |
| 多 agent 成本 15× token | fan-out 上限 5 + pause 不烧 token + 插话取消上一轮 DAG | 成本意识到位 |

**一句话**:ShadowFlow 的产品赌注(把多 agent 协作的「规格/治理/验证」做成确定性、可校验的平台原语)正好命中 MAST 实证出的最大失败类别(规格设计 42% + 验证 21% ≈ 63%)。领域共识也在从「堆 agent」转向「**确定性骨架 + 上下文工程 + 协议互通**」,与 ShadowFlow 的 DAG + Rule + ACP 路线同向。
