# 接口对接说明

这份文档写给三类人：做页面的、接支付的、接模型的。
看完应该能独立开工，不用来问「这个字段叫什么」「为什么金额差一百倍」。

后端自检入口：`GET /api/meta` 会返回当前版本的全部能力与字段清单，本文只是它的说明版。
两者冲突时**以 `/api/meta` 为准**，因为它每次启动都会跟着代码走。

---

## 一、三条链路，各进各的门

| 谁 | 入口 | 认证方式 |
| --- | --- | --- |
| 买家 | `/shop` 挑服务 → `/q/pay/{order_id}?k=...` 看进度和交付 | 下单后返回的 `access_key`，放在 `?k=` 或 `X-Order-Key` 头 |
| 老板 | `/os` 管理台 | 本机直接可用；跨机器要设 `SF_ADMIN_TOKEN`，页面右上角填同一串 |
| 外部系统 | `/api/*` | 同老板侧。写接口一律要求管理凭证 |

公开接口只有这几个：`/api/health`、`/api/meta`、`/api/products`、`/api/qr`、`/api/pay/notify`，以及 `POST /api/orders`（下单本身对买家开放）。

**订单凭据不可猜**：`ord_` 开头的单号是随机的，但没有 `ak_` 凭据仍然拿不到内容，只会得到 403。
所以前端把带 `k=` 的完整链接给客户是安全的。

## 二、约定（这几条踩过坑，务必先看）

### 1. 金额：以 `*_cents` 为准，`*_yuan` 只用于展示

```
amount_cents: 2900      ← 整数分，唯一权威值
amount: 29.0            ← 元，方便展示
amount_text: "¥29"      ← 直接可打印
```

后端已经在订单、商品、支付凭据里都同时给了这三种形态。**不要在页面里自己写 `/100`** ——
一个页面上有几处金额，就多几个写错的机会，错一处就是差一百倍。

### 2. 时间：`2026-11-04T14:07:44.660`，本地时间，无时区后缀

排序、比较请按字符串或解析后处理；跨时区展示请自行加 `+08:00`。

### 3. 状态值是英文枚举，展示文案在前端映射

- 订单：`created / pending_payment / paid / running / delivered / failed / cancelled / refunded`
- 项目：`planning / ready / executing / delivered / cancelled`
- 任务：`todo / blocked / running / review / done / failed / cancelled`

后端不会返回中文状态，因为中文会随时被改（我们已经改过一轮术语）。
前端按枚举分支，别按文案分支。

### 4. 列表会截断，别拿明细加总

`GET /api/company/{id}/pnl` 同时返回 `pnl`（全量汇总）和 `ledger`（最近 N 条明细）。
两者口径不同：

```json
{
  "pnl": {"revenue": 1377.0, "cost": 207.42, "...": "..."},
  "ledger": [ "... 最多 limit 条 ..." ],
  "ledger_meta": {"returned": 50, "total": 87, "truncated": true,
                  "note": "pnl 为全量汇总；ledger 仅为最近若干条明细，不可直接求和当作总额"}
}
```

`truncated: true` 表示还有更早的流水没返回。要总额就看 `pnl.revenue`。

### 5. ID 前缀说明含义

`ord_` 订单、`prj_` 项目、`tsk_` 任务、`emp_` 员工、`app_`/审批、`led_` 流水、`co_` 公司、`ak_` 订单凭据。
日志和客服对话里看到前缀就知道该查哪张表。

## 三、买家侧接口（做页面的重点看这段）

### 下单

```
POST /api/orders
{ "product_id": "svc_content", "buyer_name": "磨豆实验室", "contact": "", "requirement": "给手动磨豆机写小红书文案，199 元" }
```

返回：

```json
{
  "order": {"id": "ord_xxx", "status": "pending_payment", "access_key": "ak_xxx",
            "amount_cents": 2900, "amount": 29.0, "amount_text": "¥29"},
  "payment": {"provider": "local-sandbox", "mode": "simulated", "txn_id": "sim_xxx",
              "qr_text": "http://.../q/pay/ord_xxx?k=ak_xxx", "pay_path": "/q/pay/ord_xxx?k=ak_xxx",
              "amount_cents": 2900, "amount": 29.0, "amount_text": "¥29"},
  "idempotent": false
}
```

规则：

- `requirement` 至少 4 个字，最多 2000 字。超了直接 422，**不会静默截断**——被截掉的可能是客户最在意的条件。
- 十分钟内、同一个人、同一服务、**同一句需求**且还没付款的，会复用原来那张单（`idempotent: true`），避免误点两次。改一个字就是新单。
- 传错类型（比如 `requirement` 传成对象）返回 422 并说明原因，不会 500。

### 查进度

```
GET /api/orders/{order_id}?k={access_key}
```

关键字段：

```json
{
  "order": {"status": "running", "amount_text": "¥29"},
  "steps": [{"title": "先定卖给谁", "agent": "选品研究员", "status": "done"}, "..."],
  "events": [{"seq": 1, "type": "order.created", "ts": "..."}]
}
```

`steps` 已按环节聚合，回滚重做不会出现重复条目。前端照这个数组渲染进度条即可。

### 交付物（只在 `status = delivered` 时存在）

```json
{
  "deliverable": {
    "final_text": "……客户能直接读的正文……",
    "quality": {
      "score": 91, "verdict": "自检 91 分 · 可以发出", "passed": true,
      "items": [{"key": "topic", "name": "对题", "score": 29, "weight": 30, "ok": true, "note": "..."}],
      "form": {"wanted": "copy", "label": "文案", "fit": true, "note": "客户要文案，形态对得上"},
      "polish": ["内部索引", "行话"],
      "rework": {"task": "写三版广告词", "score_before": 58, "score_after": 91}
    },
    "nodes": [{"title": "...", "agent": "文案", "status": "done"}],
    "evidence": {"iterations": 9, "checkpoints": 2, "events": 9},
    "cost_cents": 1304
  }
}
```

- `quality.items` 固定四项：对题 / 能照做 / 分量 / 有交代。少一项就是后端改了，来找后端。
- `quality.form`（契约 1.4）：形态是否对题，和四项分开给。`fit = false` 表示客户要成品、
  交上来是工作底稿，此时 `score` 封顶 55、`passed = false`。前端想显示就显示，不读也不影响渲染。
- `polish` 是「出街前替他清掉的内部说法」，为空数组表示没清。
- `rework` 只在真的返工过时出现；`rework.kept == "original"` 表示补过一次没变好，留了原稿。

### 文件包下载（契约 1.5）

客户要的是「能发给别人的文件」，不是一串网页正文。三个接口，凭据同样是 `?k=`：

| 接口 | 用途 | 返回 |
| --- | --- | --- |
| `GET /api/orders/{order_id}/package` | 清单：包里有哪些文件、多大 | JSON（`files[]`、`total_bytes`、`download`） |
| `GET /api/orders/{order_id}/package.zip` | 下载 ZIP | 二进制，`Content-Disposition: attachment` |
| `GET /api/orders/{order_id}/package.pdf` | 下载交付单 PDF | 同上 |

前端注意三点：

1. **下载用 `<a href download>`，别用 fetch 再转 blob**。凭据在 URL 上，浏览器原生下载最省事；
   fetch 方案要自己处理 header 里的中文文件名，容易踩坑。
2. **先看清单再给按钮**：`available.pdf = false` 时不要显示 PDF 按钮（服务端没装 reportlab），
   `download.pdf` 这时是 `null`。
3. **只在 `delivered` 状态给入口**。未交付调这两个接口是 `404`，格式乱传是 `400`，都不是 500。

```json
{
  "order_id": "ord_ca3f2f0a20",
  "files": [{"name": "交付正文.txt", "bytes": 3402}],
  "total_bytes": 35306,
  "formats": ["zip", "pdf"],
  "available": {"zip": true, "pdf": true, "pdf_font": "simhei.ttf", "note": null},
  "download": {"zip": "/api/orders/{order_id}/package.zip",
               "pdf": "/api/orders/{order_id}/package.pdf"}
}
```

ZIP 内是一个 `ShadowFlow-交付-{order_id}/` 目录：交付说明、交付正文（txt + md）、质检报告、订单信息、附录。
`交付正文.txt` 与 `deliverable.final_text` 逐字一致——客户改稿不会改错版本。

### 订单状态推送（契约 1.6）

查订单是「问一次答一次」，这条是「有事我叫你」。页面打开就挂上，客户不用盯着刷新：

```
GET /api/orders/{order_id}/events?k=<凭据>     Content-Type: text/event-stream
```

- 事件带 `event:` 名，例如 `order.paid`、`order.delivered`；`data` 是 JSON（`id`/`type`/`at`/`order_id`/`data`）。
- 断线重连由浏览器 `EventSource` 自己做，带上 `Last-Event-ID`，中间漏的事件后端补发。
- **仍然要留兜底轮询**（我们买家页是 6 秒）：推送断了不至于一直显示「生产中」。
- 收到 `order.delivered` / `order.failed` / `order.refunded` / `order.cancelled` 后可以 `close()`，这一单已经结束。

```js
const es = new EventSource('/api/orders/' + id + '/events?k=' + key);
['order.paid', 'order.delivered', 'order.failed'].forEach(t => es.addEventListener(t, loadOrder));
```

## 五、运维接口（只有老板侧能调）

```
GET  /api/ops/status    订单积压、卡住的单、账务缺口、库体检
POST /api/ops/recover   手动续跑卡住的单（默认只捞 10 分钟没动过的）
```

`/api/ops/status` 返回里三个数字要会看：

```json
{
  "orders": {"total": 24, "by_status": {"delivered": 24}, "inflight": 0, "workers": 4, "queue_limit": 200},
  "stuck": [],
  "books": {"count": 0, "amount_cents": 0},
  "db": {"size_kb": 1900, "tables": 19, "wal_kb": 64, "ok": true}
}
```

- `stuck` 非空 = 有单挂着但没在推进，跑一次 `recover` 就好。
- `books.count` 非空 = 有已交付没收钱的单，**启动时会自动补**，这里只是让你看得见。

### 5.1 员工经验（契约 2.0 → 2.1）

```
GET    /api/company/{id}/memories           记忆列表（可按 role / service_id 过滤）
POST   /api/company/{id}/memories           手动钉一条经验
DELETE /api/company/{id}/memories/{mid}     归档一条记忆
```

前端不用接这个也能用——**记忆是系统自己记、自己带进提示词的**，不经过前端。
接它只是为了在管理台上让老板看见「这帮人学到了什么」，以及能删掉记错的。

`kind` 三个值：`lesson`（被打回的教训）、`preference`（客户提过的事）、`weakness`（反复掉分的项）。
`source` 说明它从哪来：`rework` / `client_feedback` / `quality` / `manual`（人手动钉的）。

`POST` 请求体：`{"content": "...", "kind": "preference", "role": "copywriter", "service_id": "svc_content"}`。
`role` 与 `service_id` 留空 = 不限岗位不限服务。

### 5.2 每日待办 / 调度器（契约 2.1）

```
GET  /api/company/{id}/brief              今天的待办
GET  /api/company/{id}/brief/history      历史待办（一天一份）
POST /api/company/{id}/brief/generate     立刻手动扫一遍
GET  /api/brief/scheduler                 调度器状态
POST /api/brief/scheduler/run             手动跑一轮所有公司
```

`GET /brief` 的返回多了三个字段：`generated_at`（生成时间）、`source`（`scheduler`/`manual`/`live`）、
`persisted`（是不是落库那份）。前端用来区分「系统自动扫出来的」和「实时算的」——
演示时这句话很值钱：「这是它自己每天早上扫出来的，不是我打开页面才有。」

调度器默认每天 8 点跑，可用环境变量改：`SF_BRIEF_ENABLED` / `SF_BRIEF_HOUR` / `SF_BRIEF_WEBHOOK`。
配了 `SF_BRIEF_WEBHOOK`（企业微信机器人、飞书、自建服务都行）就会把当天待办推出去，markdown 格式。

## 六、错误码

| 状态码 | 含义 | 前端怎么处理 |
| --- | --- | --- |
| 400 | 参数不合法（金额为负、回调凭据不匹配） | 提示原文 |
| 401 | 缺管理令牌 | 弹令牌输入框 |
| 403 | 不是本机 / 令牌错 / 订单凭据错 | 提示重新拿链接 |
| 404 | 订单、项目、公司、服务不存在 | 回列表页 |
| 409 | 状态冲突（已交付还要取消、任务不在可执行态） | 刷新后重试 |
| 422 | 必填缺失或类型不对 | 指出哪个字段 |
| 503 | 支付通道未配置、队列已满 | 稍后重试 |

所有错误响应都是 `{"detail": "中文说明"}`。**按状态码分支，不要按文案分支**——文案会被改成白话。

## 七、接支付要做的事

现在是沙箱模式（`SF_PAY_MODE=simulated`），扫码后点确认就回调成功，不扣真钱。

接真实网关需要补三样，位置都已经留好：

1. `app/pay.py` 的 `create_payment()`：调商户下单接口拿 `code_url` / 预支付 ID，填进返回结构。
2. `app/pay.py` 的 `verify_callback()`：换成真实验签（V3 证书 + 平台证书 + 时间戳防重放）。
3. 回调统一走 `POST /api/pay/notify`，**不用新增路由**。状态机、幂等、收入记账都已经接在这条路上。

幂等由两层保证：订单状态条件更新（`WHERE status IN ('paid','running')`）+ 账本 `(kind, ref_id)` 唯一索引。
重复回调不会重复记账，返回 `idempotent: true`。

## 八、接模型要做的事

设两个环境变量就切过去，代码不用改：

```
SF_LLM_BASE_URL=https://api.deepseek.com/v1
SF_LLM_API_KEY=sk-...
SF_LLM_MODEL=deepseek-chat
```

`app/llm.py` 是唯一的插座，`call()` 是唯一入口。切换后：

- 交付内容由真模型生成，质量自检的分数会真的随内容变化（现在模拟器下返工后分数常常不变，这是如实展示）。
- 成本按 `MODEL_CATALOG` 里的单价与实际 token 计算，会进账本。
- 提示词在 `company._build_prompt()`，带客户原话、项目上下文、上游交接内容。

## 九、改了接口怎么通知别人

1. 改字段 → 同步改 `app/contract.py` 里的 `fields` 清单，并把 `CONTRACT_VERSION` 加一位。
2. 跑 `python tools/contractcheck.py --base http://127.0.0.1:8787`，全绿才算没破坏别人。
3. 新增/删除端点 → 同步改 `docs/API.md` 的端点表（漏了 `aligncheck.py` 会报「新接口未收录」）。
4. 在本文末尾的变更记录里写一行，`CONTRACT_VERSION` 那一栏别漏。
5. **纯内部实现改动（算法、SQL、修 bug、性能）不必改任何文档**；完整对照表见 `README.md` 最后一节「继续开发时，文档怎么跟着改」。

```bash
python tools/aligncheck.py                                  # 前后端有没有对不上的接口（不用起服务）
python tools/contractcheck.py --base http://127.0.0.1:8787   # 字段契约
python tools/fuzzcheck.py    --base http://127.0.0.1:8787   # 脏输入不 5xx
python tools/opccheck.py     .tmp/shots                     # 管理台逐页截图
python tools/buyercheck.py   .tmp/buy                       # 买家页全流程
```
