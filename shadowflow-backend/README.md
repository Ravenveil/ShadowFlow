# ShadowFlow 后端引擎（MVP）

截图里 ① 号位（后端：引擎 · 知识库 · 多智能体协作）的可运行初步产品。目标就四句话：

1. **Loop 引擎与 DAG 编排跑稳跑通** —— 循环是一等公民节点，逐轮写证据链，能急停、能断点续跑。
2. **知识库 RAG 补齐配置与检索链路** —— 词条入库、分块、混合检索、引用回传，`LIGHTRAG_ENABLED` 开关与能力盘点口径一致。
3. **多智能体协作稳定输出，为前端演示供好接口** —— 每一步都是一个带 seq 的事件，前端订阅 SSE 即可复刻全过程，不需要读引擎内部。
4. **交易闭环：扫码 → 付款 → 自动交付** —— 买家扫码提需求并付款，付款回调直接建工单交给 Agent 团队，跑完原地交付，全过程留痕。

> 前三条是 PPT 承诺，第四条是队友分工新增。两者的关系不是并列功能，而是一条链：
> `扫码下单 → 付款建单 → 团队执行 → 交付回传`，前三条能力跑在第三段里。

## 快速开始

**只想看效果，三步：**

1. 双击 `start.bat`（Windows）或执行 `sh start.sh`（mac/Linux）
2. 等出现 `Uvicorn running on http://127.0.0.1:8787`
3. 浏览器打开 <http://127.0.0.1:8787/?autorun=1> —— 会自动跑一次完整任务，约 8 秒

需要 Python 3.9+。脚本会自动装依赖：`fastapi`、`uvicorn`、`segno`（二维码）、`reportlab`（导出 PDF 交付单）。
`reportlab` 可以不装——不装只影响 PDF 下载，ZIP 文件包和其余功能照常。

手动方式：

```bash
cd shadowflow-backend
python -m pip install -r requirements.txt
python run.py                 # http://127.0.0.1:8787
```

打开 <http://127.0.0.1:8787> 就是演示控制台；想一进来直接起一次完整运行，用 `?autorun=1`。

想看买家侧（扫码下单），打开 <http://127.0.0.1:8787/shop>。要让手机真的扫得动，用
`SF_HOST=0.0.0.0 python run.py` 启动，并保证手机与电脑在同一个 WiFi —— 二维码里的地址会自动取局域网 IP。

默认**不依赖任何外部服务**：没配模型 Key 时走确定性模拟器，链路、事件、证据链与真实模型完全一致，方便反复彩排。
第一次启动会自动建 `data/shadowflow.db` 并写入种子数据（演示团队 + 10 条词条），删掉 `data/` 即可回到初始状态。

接入真实模型（OpenAI 兼容），两种方式任选：

**方式一：项目根建 `.env`（推荐，不用每次设环境变量）**

```bash
cp .env.example .env          # Windows: copy .env.example .env
# 编辑 .env 填三行（模板里已给 DeepSeek / OpenAI / 通义 / Kimi 示例）：
#   SF_LLM_BASE_URL=https://api.deepseek.com/v1
#   SF_LLM_API_KEY=sk-...
#   SF_LLM_MODEL=deepseek-chat
python tools/llmcheck.py      # 退出码 0 才算真接通（会真发一次请求）
python run.py
```

**方式二：直接设环境变量**（优先级高于 `.env`）

```bash
export SF_LLM_BASE_URL=https://api.xxx.com/v1
export SF_LLM_API_KEY=sk-...
export SF_LLM_MODEL=gpt-4o-mini
python run.py
```

`base_url` 结尾带不带 `/v1` 都行，会自动补成 `.../v1/chat/completions`。
配好后 `/api/health` 的 `llm.mode` 应为 `live`；若显示 `simulated(fallback)`，
看同处的 `llm.last.error` 即可知道是 key、地址还是网络的问题。

| 环境变量 | 默认 | 说明 |
| --- | --- | --- |
| `SF_PORT` | 8787 | 服务端口 |
| `SF_HOST` | 127.0.0.1 | 设 `0.0.0.0` 后手机才能扫码打开（同一 WiFi） |
| `SF_PAY_MODE` | simulated | 支付网关：`simulated` / `wechat` / `alipay` |
| `SF_PUBLIC_BASE_URL` | 空 | 二维码里写的对外地址；留空时自动用局域网 IP |
| `LIGHTRAG_ENABLED` | 1 | 设 0 时检索链路旁路返回 stub（复刻 P10 口径） |
| `SF_KB_TOP_K` | 4 | 每轮检索条数 |
| `SF_LOOP_MAX_DEPTH` | 4 | 循环嵌套上限 |
| `SF_MAX_ROLLBACKS` | 2 | 单次运行的驳回回滚上限 |
| `SF_STEP_DELAY` | 0.35 | 每步停留秒数，只为让演示看得清；设 0 关掉 |
| `SF_DATA_DIR` | ./data | SQLite 与运行数据目录 |

## 一次运行会发生什么

默认团队「OPC 出海增长小组」：`情报侦察 → 策略定盘 → 内容打磨闭环(loop) → 合规审核 → 交付汇总`。

实际跑出来的时间线（43 条事件，可直接对照控制台）：

```
1  起跑          任务入队，记录 llm/kb 模式
2  派发 情报侦察
3  汇报 情报侦察   （带 3 条 KB 引用）
...
8  循环 内容打磨闭环  最多 4 轮 / 阈值 0.85
10 初稿 0.60 → 未达标，继续
15 二稿 0.75 → 未达标，继续
20 定稿 0.90 → 达标，收敛退出        每轮写一条 IterationRecord + 一个 checkpoint
26 合规审核 REJECT（风险 + 必须修改项）
28 回滚至「内容打磨闭环」上一轮断点
31 内容撰写（携带法务意见）0.90 达标
37 合规审核 APPROVE
39 人工门：合规 → 交付需审批（演示环境自动放行）
41 交付汇总
43 完成
```

这就是"驳回不是报错，是流程"的可演示版本：被拒产出不落库，任务自动重排给上游，第二次一轮过。

## 交易链路：扫码 → 付款 → 自动交付

打开 <http://127.0.0.1:8787/shop> 是服务台，三个上架服务各带一个二维码。

```
买家手机扫码
   ↓  填一句话需求（必填）、称呼、联系方式（选填）
POST /api/orders            建单，返回支付凭据（沙箱里是一个付钱链接）
   ↓  点「确认支付」
POST /api/pay/notify        统一回调：验签 → 幂等 → 订单置 paid
   ↓  付款即开工，不等人工接单
POST /api/runs（内部）      需求直接成为本次 run 的任务描述
   ↓  Agent 团队按 DAG 执行，驳回回滚照常
GET /api/orders/{id}        买家页轮询，看到每个环节的真实状态
   ↓  run completed
订单置 delivered            附交付物 + 证据摘要（几轮审校、几个回溯点）
```

订单状态机（单向，除退款）：

```
created → pending_payment → paid → running → delivered
                                  ↘ failed
   未付款 → cancelled        已付款 → refunded（人工确认）
```

**支付是沙箱，这一点必须对使用者说清楚。** 真实收款需要商户号，而微信支付与支付宝的商户号都要求企业资质，个人申请不下来，也就没有可用的支付回调 —— 所以「扫码付钱、自动开工」在个人主体下做不到闭环。

本仓库的处理方式是**可切换网关**（`app/pay.py`），和模型层的模拟器同一套哲学：

| `SF_PAY_MODE` | 行为 |
| --- | --- |
| `simulated`（默认） | 本地沙箱，点确认即回调成功，**不扣真实款项**，演示可重复 |
| `wechat` | 需要 `SF_WECHAT_MCHID` / `SF_WECHAT_APPID` / `SF_WECHAT_API_KEY` |
| `alipay` | 需要 `SF_ALIPAY_APPID` / `SF_ALIPAY_PRIVATE_KEY` |

缺配置时**直接报 503，绝不静默降级成假成功** —— 演示时假成功比报错更危险。
回调路由 `/api/pay/notify`、幂等处理、订单状态机都已经按真实网关的形状写好，
将来补上商户号与签名验证即可切换，前端页面与引擎一行都不用改。

## OPC OS：把引擎变成一家公司

打开 <http://127.0.0.1:8787/api/os> 是管理台。默认已经开好一家公司：**增长工场 Growth Studio**，AI 增长营销赛道，5 个部门 9 名数字员工，启动资金 2000 元。

### 五层结构

```
老板（人）      目标制定 · 关键审批 · 经营决策
   ↓
公司层          组织架构 · 员工名册 · 审批流 · 经营账本     ← 本次新增
   ↓
任务层          项目 · 任务协议 · 交接 · 成本归集            ← 本次新增
   ↓
执行层          DAG · Loop · 策略矩阵 · 知识库 · 模型        ← 已有
   ↓
交付层          订单 · 交付物 · 收款                          ← 已有
```

前两层是这次补的，后两层是前几轮已经跑通的。**新增的层不碰模型调用细节，只决定「谁、在什么授权下、做什么、花多少钱」。**

### 员工不是一段 prompt

九个员工各自带岗位、部门、技能、权限、模型、日成本、绩效和状态：

| 员工 | 岗位 | 部门 | 模型 |
| --- | --- | --- | --- |
| 陈明远 | CEO 助理 · 项目经理 | 总经办 | Claude Sonnet |
| 苏策 | 品牌策划师 | 品牌策略部 | Claude Sonnet |
| 陆审 | 质量审核 | 品牌策略部 | Claude Sonnet |
| 罗法 | 合规审核 | 品牌策略部 | Qwen Max |
| 林研 | 市场研究员 | 市场研究部 | GPT-4o |
| 周数 | 数据分析师 | 市场研究部 | DeepSeek V3 |
| 何文 | 文案运营 | 创意制作部 | DeepSeek V3 |
| 江设 | 视觉设计师 | 创意制作部 | Gemini Flash |
| 沈客 | 客户经理 | 客户成功部 | GPT-4o |

五种模型跑在同一个框架里，按岗位分工：需要判断力和文风的岗位用旗舰模型，批量化、结构化的岗位用性价比模型。模型单价写进 `MODEL_CATALOG`，每个任务的成本可以逐笔核算。

### 剧本按服务定制：不同的单子走不同的流程

员工编制固定 9 人，但「这次要做什么」由剧本决定。剧本是一张依赖图，`after` 指向的上游完成才可执行，同一批上游天然并行。`app/seed_data.py` 里三套：

| 服务 | 剧本 | 环节数 | 流程 |
| --- | --- | --- | --- |
| 出海选品包 | `PLAYBOOK_SELECTION` | 9 | 排期 → 市场扫描 → 选品策略 → 文案／视觉（并行）→ 利润测算 → 执行动作表 → 复核 → 合规 |
| 上架前体检 | `PLAYBOOK_COMPLIANCE` | 7 | 预审范围 → 准入扫描 → 用语自查 → 整改文案／标识规范（并行）→ 风险定级 → 合规放行 |
| 推广文案包 | `PLAYBOOK_CONTENT` | 7 | 目标确认 → 卖点提炼 → 内容角度 → 多版本文案／配图（并行）→ 审校 → 合规过闸 |

下单时 `orders.py` 按 `product_id` 取对应剧本（`seed_data.playbook_for()`），所以卖什么就按什么流程干，不会拿本地门店那套去做出海单子。

**模拟器的口径**：未配 LLM Key 时，产出是「该岗位的结构化作业稿」——只引用真实输入（项目目标、客户、任务要求），需要数据的地方写明查什么、从哪查，**不编造市场数字**。同一输入同一输出，方便演示时反复对比。配了 `SF_LLM_API_KEY` 后走真实模型，产出才是针对该市场的结论。

### 任务协议：一个任务必须能追到五件事

`app/company.py` 里的任务不是待办事项，是一份契约：

| 要素 | 落在哪 | 用途 |
| --- | --- | --- |
| 责任人 | `assignee_employee_id` | 谁做的，可追到员工卡片 |
| 执行过程 | `run_id` + 事件流 | 每一轮怎么想的、改了什么 |
| 交接记录 | `handoff_json` | 上下游交付了什么，不用重读全库 |
| 成本 | `cost_cents` + `ledger` | 模型费 + 工时分摊，进账本 |
| 交付结果 | `output_json` | 正文、摘要、引用、tokens |

### 风险分级：哪些决策必须人来做

| 风险 | 谁来批 | 例子 |
| --- | --- | --- |
| `low` | 自动放行 | 内部调研、分析、文案初稿 |
| `medium` | 老板在管理台点通过 | 对外物料（视觉、投放素材） |
| `high` | 老板本人，不可跳过 | 合规审查、对外发布 |

演示时最能说明问题的一幕：项目跑到「视觉物料设计」会**停下来等你**，一路「继续执行」推到「合规审查」又停下一次。这两次停顿就是「哪些决策需要人」的答案。

> 客户已付款的订单走另一条规则：审批照常生成、照常留痕，但由系统代老板放行，
> 避免客户卡在公司内部流程上。这个取舍在 `orders._execute_project` 里，一眼可见。

### 经营数据是真的

每一个任务执行完都会写一条账本流水：模型调用成本（按 tokens × 单价）加上工时分摊（日成本 ÷ 8）。订单交付时自动记一笔收入。所以首页那四个数字不是装饰：

```
营收 ¥499　成本 ¥79　毛利 ¥420　毛利率 84.2%
```

这个成本结构就是「一人公司」的账：人力成本几乎为零，主要成本是模型调用与极少量工时。

### 和交易链路是接上的

客户扫码下单付款之后，**那一单直接变成公司的一个项目**，走组织、走任务依赖、走审批，而不是另起一套流程：

```
扫码付款 → 建项目 → 按剧本拆成 9 个任务 → 并行执行
       → 两次审批（系统代批，留痕） → 项目 delivered
       → 订单 delivered + 自动记收入 → 客户端看到交付物
```

### 发货前自检：机器先挑自己的毛病（v0.4.0）

`done` 只说明流程走完了，不说明东西能看。所以交付前多一道闸门（`app/quality.py`），
四条能算出来的硬指标，不打感情分：

| 指标 | 权重 | 在问什么 |
| --- | --- | --- |
| 对题 | 30 | 客户原话里的诉求，交付里回应了没有 |
| 能照做 | 25 | 有没有具体数字（价格、天数、数量、比例） |
| 分量 | 25 | 字数够不够该服务的底线 |
| 有交代 | 20 | 下一步先干什么、哪里会踩坑，说清了没有 |

同一份输入永远同一个分（纯函数，可单测）。低于 62 分不硬发，而是把**最弱的那一环**
退回重做一次；重做时把自检意见作为「打回理由」传给执行者。改完如果没变好，
就**保留原来那一版** —— 返工不保证更好，但保证不变差。返工痕迹会写进交付页，不装作一次做对。

另外一道是「出街清洗」：`引用词条：证据链 IterationRecord、Loop 循环引擎与 PDCA`
这种我们自己看的索引，客户只会觉得莫名其妙，交付前直接摘掉，能换白话的换掉，
清了几处如实写在交付页上。

```
GET /api/orders/{id} → deliverable.quality
{
  "score": 93, "passed": true,
  "verdict": "自检 93 分 · 可以发出",
  "items": [{"name": "对题", "score": 30, "weight": 30, "note": "客户诉求命中 71%"}, ...],
  "polish": [], "rework": {"score_before": 58, "score_after": 93, "task": "挑出卖点"}
}
```

### 客户资产：值钱的不是这一单（v0.4.0）

订单表里有名字、有金额、有交付时间，但没人把它当资产看。`customer_book()` 把这些散落的名字
收成一份客户表：买过几次、花了多少、毛利多少、交付自检平均几分、下一步该卖什么、多久没联系。

- **复购阶段**：新客 / 复购 / 老客，按实付订单数自动分。
- **下一步卖什么**：按「买完这一样，下一件缺什么」的顺序推荐 —— 选品 → 体检 → 文案 → 打包价，
  不是随机推贵的。
- **回访雷达**：超过 7 天没联系标记「该回访」；刚交付的写「先别催」。

```
GET /api/company/{id}/customers
{ "summary": {"customers": 5, "repeat_rate": 80.0, "avg_per_customer": 175.6, "due": 0}, "items": [...] }
```

### 每天一张简报：今天该动哪几件事（v0.4.0）

总览页顶部那张卡不是问候语，是从账本、审批、客户表里算出来的：

- 有单要拍板 → 列出来，标明高风险必须本人；
- 有客户到期没联系 → 点名，并给出下一句该问什么；
- 服务毛利排名 → 最赚的那门「报价别自己往下压」，毛利过 88% 且单量够的建议提价 10%，
  低于 65% 的建议提价或砍掉最费时的环节。

```
GET /api/company/{id}/brief
{ "headline": "今天有 1 件要你点头，2 个客户该回访", "actions": [...], "advice": [...], "stats": {...} }
```

这三块合起来是一条闭环：**做完 → 自检 → 留档 → 回访 → 定价**。

### 后端加固：让「已付款的单一定会被推完」（v0.4.1）

演示时最怕的不是慢，是卡住不动。这一版把后台执行链路上的几个真问题堵了：

**一、进程死了，单不能跟着死**

后台推进原本只活在内存线程池里。服务一旦重启（Ctrl+C、断电、换版本），
数据库里那行还写着 `running`，但没有任何线程在推它，客户会永远看到「团队正在为你工作」。

现在启动时扫一遍 `paid / running` 的订单，能收口的收口，没收口的重新投递；
另外每 20 秒有一次补位，只捞「一分钟没动过」的单。订单事件里会留下 `order.resumed` 的痕迹。

**二、并发超过线程池，排队而不是丢单**

原来的逻辑是：拿不到槽位就发一个 `queued` 事件——那等于把单扔了，因为没东西会回头再推。
现在池满就排队，只有排队堆到 200 才拒单（背压）；配合每 20 秒的补位，排队一定会被消化。

同一个项目加了推进互斥：并发投递 10 次也只执行 1 次，不会两个线程抢到同一批任务重复做、重复记成本。

**三、失败有上限，不在后台无限重试**

单次失败大概率是瞬时问题（库锁、进程忙），重试是对的；连续 3 次还失败，说明这单有硬问题，
订单直接标 `failed`，项目停掉，事件里写明原因。**不会为了「看起来还在进行」而一直烧成本。**

**四、账要对得上**

发生过的真事：两单已交付却没记收入（走的是早期路径，那一刻没人记账，而它不会再变一次）。
当时账本收入 1179、已交付订单合计 878，差 301——其中 198 是那两单漏记，
另外 499 是一笔「先收款后立项」的首期款（本来就没有对应订单）。
两个原因混在一起，演示时被问「这两个数为什么不一样」很难解释清楚。

现在 `/api/ops/status` 会显示这个缺口，启动时也会自动对账补记（幂等，重复跑不会多记一分钱）。
目前主库已补齐，缺口为 0。

**五、脏输入不再打成 500**

前端传错类型是常事：`requirement` 传成对象、`buyer_name` 传成数组，原来直接 `.strip()` 就是 500。
现在非字符串一律收敛，由接口给出 422 并说明原因。`tools/fuzzcheck.py` 会把 14 个写接口
用空值/类型错乱/超长字符串各打一遍，当前全绿。

另外两处顺手修的：需求超 2000 字不再静默截断（截掉的可能正是客户最在意的条件，改为 422 提示）；
十分钟内同一个人、同一服务、同一句需求的未付单会复用，避免买家连点两下在后台多跑一整个项目。
不是三个孤立功能，是同一份数据被用了三次。

## 四个演示动作

**A. 主线（约 8 秒）**：控制台点「开始执行」。看 DAG 节点颜色流转、右侧逐轮得分 0.60 → 0.75 → 0.90、事件流里法务驳回与回滚。

**B. 急停 + 断点续跑**：跑起来后点「急停」，状态变 stopped，checkpoint 已落库；点「断点续跑」，从最近断点接着跑完，已完成的节点会打 `node.skipped`。

```bash
curl -X POST http://127.0.0.1:8787/api/runs/<id>/stop
curl -X POST http://127.0.0.1:8787/api/runs/<id>/resume
```

**C. 策略矩阵拦截**：左侧选「内容撰写 → 合规审核」，点「查表判定」，返回 `deny`；点「编译期校验」，任意塞一个 `writer → legal` 的直连团队，会拿到四眼原则错误并拒绝保存。

### 接真实模型：从「作业骨架」到「能直接发」（v0.4.2）

前几版的交付物有个隐性天花板：没配 Key 时，模拟器给的是「该岗位的作业稿」——告诉你去查什么、怎么算，但具体数字要人填。演示够用，直接发给客户不够。

这一版把「接真模型」从"支持"做成"开箱能用"：

- **`.env` 直接生效**：项目根放一个 `.env`（照 `.env.example` 填三行），启动即读，不用每次改系统环境变量。已存在的真实环境变量优先、不被覆盖，服务器部署方式不受影响。
- **地址自动补齐**：`https://api.deepseek.com` 少了 `/v1` 也能通，程序统一补成 `/v1/chat/completions`，不再「差一个路径就 404」。
- **失败重试**：网络抖动/超时重试 2 次（4xx 配置错误不重试，直接报）；仍失败才降级到模拟器，并把原因记在 `llm.last.error`，不再"看起来在跑、其实是兜底"。
- **一键自证**：`python tools/llmcheck.py` 真发一次请求，退出码 0 才算接通；`/api/health` 的 `llm.mode` 会显示 `live` 或 `simulated(fallback)`。

接上之后，交付物从「告诉你查什么」变成「给出针对这次需求的结论」，这才是能直接发给客户的东西。

### 交付物成形：客户要的是成品，不是我们的过程记录（v0.4.3）

接上真模型后又暴露一个新问题：客户要「500 字推广文案」，收到的是 **7276 字的计划书**——里面有需求拆解、卖点分析、配图建议、审稿打分，字数超了 14 倍，质检还给了 100 分。

原因不在模型，在组装：原来把「最后一个环节的产出 + 最后 4 段实质产出」拼起来当交付，模拟器下每段都短，拼着还像样；真模型下每段都长篇，拼起来就成了内部工作底稿。

这一版把交付物重新定形：

- **正文只认「写稿的人」**：按角色（`copywriter`）取成品，不再按「谁最后说话」取。复核、合规是给我们自己把关的，不进客户的眼睛。
- **篇幅按客户说的来**：从客户原话解析字数要求（`500字左右` / `不超过300字` / `500-800字` / `至少800字`），既管道「太短」也管道「太长」。客户说 500 字给了 7276 字，`length.overlong = true`，直接判不合格——这不是「写得多了点」，是没按要求做。
- **字数当硬约束传下去**：客户的篇幅要求会写进写作任务的指令里，让写的人一开始就知道预算，而不是事后硬切。客户指定篇幅时，剧本里「5 个标题 + 2 版正文」的默认量自动作废，只交 1 版完整成品。
- **剪过就说剪过**：万一还是超了，按头尾保留裁剪（保住开头和「下一步怎么做」），中间如实标出省略，未精简的原稿放进 `appendix`，客户想看全文有地方去。
- **去排版符号**：交付前把 `##` `**` `---` 清掉，客户拿到的是能直接复制发出去的纯文本，不是一份草稿。
- **契约 1.3**：交付物新增 `quality.length`（篇幅是否照客户说的来）、`trimmed`（精简记录）、`appendix`（策划过程与未精简原稿），纯新增，前端不读也不影响渲染。

顺带修了质检的三处误判（这三处会让一篇好文案被判 54 分）：

| 误判 | 原因 | 修法 |
|---|---|---|
| 「0 处具体数字」 | 只认阿拉伯数字，文案里「三天」「两版」「一小时」全漏 | 中文数字+量词一起认，虚指（一个/一次/一遍）不计 |
| 「没写下一步」 | 文案写的是「三步：第一…」，词表只认「第一步」 | 补「三步/怎么做/发布位置」等说法 |
| 635 字落在客户要的 350–750 区间内却扣分 | 只按「接近下限」算 | 落在客户给的区间内直接算达标 |

另外，「能照做」「有交代」两项的门槛按服务区分：文案类不要求写「风险提示」（写了反而不像文案），说清「发在哪、怎么用」就算交代；数字门槛也低于咨询报告。

效果对比（同一需求：面向中小企业主的智能办公推广文案，500 字左右）：

| | 交付字数 | 形态 | 质检 |
|---|---|---|---|
| 模拟器（v0.4.1） | 1032 | 作业骨架 | 91 分 pass |
| 真模型（v0.4.2 接模型后） | **7276** | 计划书 | **100 分 pass**（误判） |
| 真模型（v0.4.3 成形后） | **660** | 一篇可直接发的文案 | 100 分 pass |

### 形态贴合：字数对了，也可能给错东西（v0.4.4）

v0.4.3 把篇幅管住了，但留下一个漏洞：**篇幅对了，东西不对**。客户要 500 字文案，理论上可以交一份「500 字的需求拆解 + 验收清单」——字数完美，全篇不是他要的。

这次把「形态」也变成可判的：

- **先判客户点的是哪道菜**：从原话认形态（文案 / 文章 / 脚本 / 邮件 / 清单 / 方案 / 报告），认不出来就不判，不硬猜。
- **证据只看标题**：正文标题里出现两个以上内部流程词（需求拆解、执行步骤、验收标准、配图建议、复核、排期…），判定为「把工作底稿发出去了」。只看标题，不看正文——文案里写一句「没有验收标准」是内容本身，不算证据。
- **只判成品型交付**：方案、报告、清单本来就可以分章节，「执行步骤 / 预算 / 风险提示」是本职；只有文案、文章、脚本、邮件这类「交出去就是成品」的形态才卡。
- **判不合格就退回去重写**：形态不对直接封顶 55 分（不是扣几分），并指定让写稿的人重写，不是随便挑最长的一段。
- **防在写之前**：形态要求同样写进写作指令——「只放成品本身，开头直接进入正文，不要写需求理解、执行步骤、验收标准」。事后判是兜底，事前说清楚才便宜。
- **契约 1.4**：交付物新增 `quality.form`（`wanted` / `fit` / `note` / `signals`），纯新增。
- **`tools/formcheck.py` 回归**：正反例写死在脚本里（正常文案 / 底稿冒充文案 / 正经方案 / 无形态要求），改判定规则后跑一遍，退出码 0 才算没改坏。这一项最容易两头出错——太松等于没闸门，太紧会把好单子打回。

拿库里的真实交付回测（同一句「500 字推广文案」的需求）：

| 交付 | 字数 | 形态判定 | 自检 |
|---|---|---|---|
| v0.4.3 成形后的文案 | 660 | 形态对得上 | 100 分 pass |
| v0.4.2 那份计划书 | 7276 | 4 个流程标题 → 工作底稿 | **55 分 fail**（原来 100 分） |
| 一份正经落地方案（客户要的就是方案） | — | 本来就可以分章节 | 不判形态，按其余四项打分 |

### 带得走的文件包：ZIP + PDF（v0.4.5）

前三步解决的是「做得对不对」，这一步解决「交得出去吗」。客户付完钱，页面能读是做给我们看的；
他真正要干的是把文案发给自己的客户、丢进群里、贴进后台——那就得有一个**双击就能打开的文件**。

- **ZIP 里放什么**（固定六类，不多不少）：
  `交付说明.txt`（这个包是什么、怎么用）、`交付正文.txt`（能直接复制）、`交付正文.md`（带标题便于二次编辑）、
  `质检报告.txt`（分数、四项明细、篇幅、形态、清洗与返工记录）、`订单信息.txt`（对账与追溯）、
  `附录/NN-*.txt`（策划过程与未精简原稿）。
- **正文逐字一致**：包里的 `交付正文.txt` 和网页上的 `final_text` 是同一份，客户改稿不会改错版本。这条由 `tools/packcheck.py` 每次发布前比对。
- **中文文件名不乱码**：ZIP 内所有条目打 UTF-8 标记，Windows 自带解压和 7-Zip 都正常显示。
- **PDF 是一张交付单**：抬头（客户/金额/交付时间/质检/篇幅/形态）+ 正文 + 质检摘要 + 附录，
  内嵌中文字体（只嵌用到的字形，一百多 KB，不是塞一个 10MB 字体进去）。
- **没有字体也不崩**：优先找系统黑体/雅黑，找不到退回 Adobe STSong-Light，再不行如实告诉前端「PDF 不可用」，ZIP 照常。
- **下载走原生链接**：`<a href download>`，凭据在 URL 上。不用 fetch 转 blob——那样得自己在 JS 里解 header 的中文文件名，容易出错。
- **先给清单再给按钮**：页面先拉 `/package` 看包里有几个文件、多大，`available.pdf=false` 时不显示 PDF 按钮。
- **契约 1.5**：新增 `order_package` 清单接口，二进制下载不入契约（字段无关），由 `tools/packcheck.py` 专门查。

实测（样单一篇 3402 字文案）：清单 11 个文件 / 35 KB，ZIP 18 KB，PDF 158 KB / 6 页，中文与符号（￥、√、—）都正常；
错误分支：未交付 `404`、格式乱传 `400`、不存在 `404`，没有 500。

### 页面真的联动：一条事件总线（v0.4.6）

前四步都在让「一单」做得更好，这一步解决「几个人同时看着几个页面」时的体验：
客户在手机上付完款，老板大屏还停在 8 秒前的数字上；买家页盯着「生产中」不动，其实早就交付了。
之前三个页面各刷各的（老板页 8 秒、买家页 1.5 秒、引擎台只盯自己那个 run），
用户的原话是「我这边操作了，那边没反应」——不是没做，是没到下一次轮询。

- **一处发，处处收**：`db.emit_order` / `db.emit` 写完库顺手往总线丢一条，业务代码不用改。
- **两个入口，两种权限**：管理侧 `GET /api/events`（可按 `types=order.` 前缀过滤），
  买家侧 `GET /api/orders/{id}/events`（凭据 `k=`，只推这一单）。
  总线只发 `id` 与摘要，页面收到后仍走正常接口取详情——**权限校验只有接口层一处**，不会因为推送泄数据。
- **断线不丢**：事件带全局自增 `id`，重连时浏览器带 `Last-Event-ID`，后端从环形历史（300 条）补齐。
- **推不动也不至于瞎**：页面保留兜底轮询（老板页 30 秒、买家页 6 秒）。推送是加速，不是唯一真相来源。
- **可自证**：`tools/livecheck.py` 真下一单、真付一次、再取消，验证事件在两端几秒内到达；`/api/events/stats` 能看当前几路在听。

实测：下单 → 老板侧收到 `order.created`；付款 → `order.paid`；买家侧连上能补到 `order.created, pending_payment, paid, dispatched`；
取消 → `order.refunded`（已付款的单走退款，不叫取消）。浏览器里老板页左下角从「○ 轮询」变成「● 实时」。
顺带把买家页轮询从 1.5 秒降到 6 秒、老板页从 8 秒降到 30 秒——开着页面不再每秒打十几个空请求。

**契约 1.6**：新增 `events_bus` / `order_events` 两条 SSE（契约走查只握手，字段由联动走查验）与 `events_stats`。

顺带被这条走查逼出两个真 bug，一起修了：

- **付款与取消同时发生**，会留下一个「执行中」的空项目：退款了，后台还在往里烧钱。
  现在付款后开项目前会再看一眼订单状态（不是 `paid/running` 就不建项目），
  取消/退款时也会按 `order_id` 把项目全扫一遍停掉，不只信 `order.project_id`。
- **已取消的项目赖在看板上**：退款单留下的空壳显示成「待启动」，看着像还有活儿没干。
  看板与「在手项目」都排除 `cancelled`；走查留下的测试单可以用 `tools/testdata.py` 从看板上摘掉（只改状态，不删数据）。

## 交付质量：自检别冤枉好稿（v0.4.7）

第五步之后，页面都通了，问题落在一句客户的话上：**「我这单 46 分，是不合格吗？」**
那是一篇 364 字、能直接发的小红书月饼文案。模型没写错，是尺子量错了。

四个错，全是「尺子」问题，跟模型无关：

- **对题按逐字比对客户原话**。「给一家烘焙店写中秋新品的小红书文案，300 字左右」这句话里，
  「小红书」「300 字」是格式要求，正文里当然不会出现——一段合格的小红书文案不会自己写「本文发在小红书」。
  按逐字算，这三样直接算成「没回应客户」，对题只剩 44%。现在先把形态词、篇幅词、平台词、交付动作词剥掉，
  再比对剩下的**内容诉求**。
- **数字只认「个 / 天 / 元」**。文案里的具体信息是「三盒」「半块」「一杯」——量词不认识，
  一整篇有细节的稿子被判「0 处具体数字」，25 分全扣。量词表补到 30 多个，「半」也算实数。
- **文案的 CTA 不认**。「现在预订有早鸟价」「想订的可以早点去」是标准的投放收口，
  但词表里只有「下一步 / 建议 / 发布于」这种报告口吻，于是 20 分照扣。新增一层投放场景 CTA 词表
  （预订、到店、评论区、私信、扫码、手慢无……），宁窄勿宽——「可以」「试试」这种到处都有的词放进去，空话也能蹭满分。
- **客户给了区间，还按服务底线罚**。客户说「300 字左右」（210–450），写了 198 字，
  却被拿去和「服务底线 450 × 1.35 = 607」比，扣掉 17 分。客户给了数字就按客户的数字判。

还有一个更贵的错：**返工派错了人**。低分单会退回重写一次，但「重写谁」是按**字数最长**挑的——
最长的那段通常是「配图怎么配」（2000 字），于是把配图建议重写了一遍，真正的文案一个字没动，
模型钱花了、分数一点没变。现在固定先找写稿的人（`copywriter`），没有才退而求其次。

口径修完，还得让**老单跟上**，否则客户档案里上一单 46 分、这一单 100 分，两套尺子。
所以给报告加了 `quality.rules` 版本号：口径一改，服务启动时把历史交付全部重算
（v0.4.4 是手工补 `form` 字段，v0.4.6 又补一次——这次改成版本号，以后不用再手工迁移）。

实测（同一句需求、同一个模型）：

| | 修前 | 修后 |
| --- | --- | --- |
| 那篇 364 字月饼文案 | 46 分 fail（对题 44%、数字 0、收口 0） | **100 分 pass** |
| 空话 / 纯抒情 / 跑题 | 22 / 22 / 36 | 34 / 34 / 46，**仍然是 fail** |
| 咨询报告（本来就该铺数字） | 83 warn | 83 warn，没被文案的尺子误伤 |

新增 `tools/scorecheck.py`：好稿必须 ≥85 且「能照做」「有交代」不为 0，空话/抒情/跑题必须 fail，
篇幅区间不许「底线 > 上限」，返工目标必须是写稿的人。改任何评分规则先跑它。

**契约 1.7**：交付物新增 `quality.rules`。

## 员工只查自己这单的手册（v0.4.8）

第六步之后分数公平了，但翻日志时发现一件更难堪的事：写「烘焙店中秋文案」的任务，
检索结果里躺着「出海选品怎么做（四步）」和「小件跨境一般几天到」，整段被塞进提示词。
成品没跑偏——那是模型自己忽略的结果，不是系统的设计。

根因很简单：**检索是全库召回**。词条没有「适用范围」，员工的岗位和这单是什么服务，检索时根本没参与。

- **词条有了适用范围**：`scope_services`（哪些服务用得上）+ `scope_roles`（哪些岗位用得上），
  留空 = 通用。比如「小红书种草结构」只对文案服务开放，「出海选品四步」「跨境几天到」只对选品服务开放，
  「四眼原则」只给审核/合规，「收款怎么算到账」只给客户经理；「返工怎么改」「每步留记录」是通用常识，谁都能查。
- **执行任务时按域召回**：`run_task` 把「本单服务 id + 员工岗位」传给检索，
  不属于这个域的词条连候选都进不了。项目还没关联订单（取不到服务）时，服务专属词条一律不召回——
  没有上下文就别猜。
- **管理台仍然全库搜**：`/api/kb/search` 不传 `service_id`/`role` 就是全库检索。
  排障时想知道「为什么员工没查到这条」，得能看见全部。
- **老库不会断崖**：启动时按种子 id 回填适用范围，只补空范围的种子词条，用户自己加的一律不动。
  没配范围的词条仍然是「通用」，所以升级后不会突然查不到东西。
- **顺带治了检索噪音**：`fuzzcheck` 每次往库里塞 10 条畸形词条，没有业务含义却参与召回。
  给词条加了 `archived` 归档位（记录保留、不再召回），`tools/testdata.py --apply` 顺手归档。

提示词里也补了一句「只挑和本次任务直接相关的用，不相关的当没看见，不要硬套」——
过滤是硬约束，这句是兜底，两道一起上比只靠一道稳。

实测（同一句烘焙需求，`service_id=svc_content`、`role=copywriter`）：

| | 分域前 | 分域后 |
| --- | --- | --- |
| 文案任务的检索结果 | 小红书结构、出海选品、跨境物流、一人公司… | 小红书种草结构、AI 员工怎么分工 |
| 选品任务的检索结果 | 混着内容岗的词条 | 选品四步、跨境时效、返工、分工 |
| 审核岗能查到「四眼原则」 | — | 能；文案岗查不到 |

新增 `tools/kbcheck.py`：九条硬断言——跨行业的查不到、本行业的查得到、岗位专属不跨岗、
通用词条不被锁、管理台全库搜不受影响、没上下文不召回专属词条、归档词条不参与召回、分域不能把结果清空，以及「别的进程改了库，检索要立刻看得见」。

**契约 1.8**：词条新增 `scope_services`/`scope_roles`/`archived`，检索新增两个可选参数；
`kb_status` 补 `scoped`/`common`/`archived` 三项计数。契约清单新增 `kb_entries` 一条（21 项）。

**边界**：跑单引擎（`/api/runs`，没有订单上下文的独立编排流程）仍按全库检索——
它没有「这单是什么服务」可依，硬判反而会挡掉该给的词条。

## 客户说不行，能改（v0.4.9）

前面七步把「做出来」这件事修顺了：模型是真的、形态是对题的、篇幅照客户说的、
知识库不串行、文件能带走。但有一条链还是断的——**客户收到成品之后**。

交付是终点，不是关系的终点。客户拿到东西，通常第一反应是「这里不行」：
太官方了、太长了、事实不对。之前系统对这种反馈的回应是：没有「反馈」这个概念。
客户想说，只能在外部说；我们收不到，收到了也不会变成下一版。

这一版把这条链接上，三件事，缺一件都算断：

- **收得到**：交付页多一个「哪里不对？」——点几个标签（太官方 / 不像我们说话 / 事实不对 /
  太长 / 没说到点上 / 漏了重点），再写一句。**客户原话原样存**，不改写、不总结。
- **改得动**：原话连同「上一版正文」一起交回写稿的人，重出一版。改出来是残的、或者压根没改，
  就把原版还回去，并且如实告诉客户「这一版没比原来好」——不能把更烂的东西当改进交付。
- **记得住**：同一个客户下一单，上一单的意见会进提示词（「这位客户以前提过的意见」）。
  让他把同一句抱怨说第二遍，是我们的失职。

顺带治了一个更隐蔽的毛病：**返工时真模型根本看不到打回理由**。
`rejected_reason` 以前只喂给模拟器（读 `meta`），真模型的提示词里既没有理由、
也没有上一版正文——所以「按意见重做」实际是「重写一份」，返工等于抽奖。
现在提示词里同时给「客户原话 + 客户看到的成品 + 上一版产出」，并明确要求
「不要照抄上一版」「只改被点到的地方」。

实测（真下单、真提意见、真返工，同一句烘焙文案需求）：

| 客户说 | 系统做的 | 结果 |
| --- | --- | --- |
| 「太官方了，我们店说话像邻居，别用『尊敬的客户』」 | 把敬语清单和上一版一起交回写稿人 | 改后开头是「中秋前一周，店里最忙的不是后厨，是试吃台」，敬语全无；90 → 90 分 |
| 「还是太长」 | 同上，再压一轮 | 245 字；90 → 86 分，**采纳客户的版本** |

最后一行是这次特意改的规则：**客户意见优先于自检分数**。自检分掉 4 分不是他的意见错，
是这套尺子跟他的口味不一样——他要的是更短，那就更短。只有两种情况退回原版：
压根没改出来、改出来的版本是残的。
（自检返工仍是「改差了留原版」：那是系统自己的质检，客户点名要的东西由客户说了算。）

还有一条成本纪律：**一单最多自动改两轮**，第三轮直接回「这单已经改过两版了，
剩下的我人工接」。模型改不动的通常不是多跑一次能解决的，再跑只是继续烧钱。

新增 `tools/feedbackcheck.py`：离线段四条断言（客户原话与上一版必须进提示词、
同一客户上一单的意见要进下一单、没交付不能提/太短被拦/第三轮被拒），
在线段真下一单、真提意见、真等返工，验正文真的变了、意见真的记在交付物里。
自检从八件套变九件套。

**契约 1.9**：新增 `order_feedback`、`order_feedback_submit` 两个端点；
交付物新增 `feedback` 段（`total`/`changed`/`items[]`，含客户原话、标签、状态与改前改后分数）。

**边界**：客户档案按联系方式认人（没填联系方式就按称呼），只取近半年、被采纳过的意见，
最多带三条进提示词——客户档案不是垃圾桶，塞满旧意见模型会以为每条都还成立。

## 员工会长大：跨任务长期记忆（v0.5.0）

前面九步把「这一单做对」做完了。v0.5.0 换了一个轴：**这个公司会不会积累。**

原来的缺口写在自己的文档里——*员工记得自己的技能与历史绩效，但不记得上一次项目学过什么*。
知识库是**人手动维护**的：谁都可以加词条，但没有人负责更新。于是每接一单，
「上次那单被客户打回是因为太官方」这件事，下次还得重新踩一遍。

这一版把这段补上：**系统自己在干活过程中把经验记下来，下一单自动带进提示词。**

```
上一单交付
   ↓ 自检打回 → 记住「为什么被打回」
   ↓ 客户提意见 → 记住「他说了什么」
   ↓ 某项质检没拿分 → 记住「这一项怎么自查」
   ↓
   ↓ 下一单同岗位、同服务的任务
   ↓ 提示词里自动多一段：「你自己的经验（前面几单踩过的坑…）」
   ↓
写稿的人开工前就知道上次栽在哪
```

**三个来源，全部基于已经落库的事实，不额外调模型**（省成本，也不怕幻觉）：

| 来源 | 记什么 | 例子 |
| --- | --- | --- |
| `rework` | 自检打回的原因 | 「内容打磨」被退回：缺少具体数字 |
| `client_feedback` | 客户原话 | 客户提过：太官方了，我们店说话像邻居 |
| `quality` | 反复掉分的那一项 | 自检「有交代」这项没拿分，下次写完先自查这一项 |

**和知识库、客户档案的区别**（这三样最容易混）：

| | 知识库 kb_entries | 客户档案 feedback | 记忆 memories |
| --- | --- | --- | --- |
| 谁写的 | 人手动加 | 客户说的 | **系统自动记** |
| 记什么 | 通用的方法与政策 | 这个客户提过什么 | 这次执行暴露出的**可复用教训** |
| 谁的 | 全公司 | 某一个客户 | 某个岗位 + 某类服务 |
| 例子 | 「四眼原则是什么」 | 「麦香烘焙说别太官方」 | 「文案返工三次都因为交成了工作底稿」 |

**分域口径和知识库一致**：记忆按「岗位 + 服务」召回，烘焙文案的经验不会串到出海选品去；
项目没关联订单（取不到服务）时，服务专属的记忆一条都不带——不知道是什么活，别乱套。

**记忆只影响提示词，不直接改产出。** 质检、返工、客户意见的优先级都不变，
记忆不能压过客户。记错了可以删（管理台「员工经验」页，或 `DELETE /api/company/{id}/memories/{mid}`），
删的是归档不是物理删除，留痕可查。

新增 `tools/memorycheck.py`：离线段十条断言（写入能召回、重复内容只加权不新增、
服务/岗位不匹配不召回、无上下文不召回、记忆真的进了提示词、没串到别的岗位、归档后不再召回），
在线段验端点能列出与归档。自检从九件套变十件套。

**契约 2.0**：新增 `memories` 端点（`GET /api/company/{id}/memories`）与
`DELETE /api/company/{id}/memories/{mid}`；`/api/meta` 的 `capabilities` 新增 `long_term_memory`。

**顺带治了一个真问题**：`tools/fuzzcheck.py` 每跑一次就往库里塞一条畸形词条，
它没有业务含义却参与召回——真出过一条漏网的 fuzz 词条排在召回第一位（score 1.27）。
以前靠人记得跑 `tools/testdata.py --apply`，漏一次就漏一条。
现在 **fuzzcheck 跑完自己把造的词条归档掉**，不指望人记得。

## 老板不打开页面，系统也知道该干什么（v0.5.1）

前面十步把「这一单做对」和「这个公司会不会积累」都做完了。v0.5.1 补的是最后一环：
**没人看着的时候，公司自己转。**

原来的缺口很具体：管理台总览顶上那张「今天先做这几件」是**打开页面才现算**的。
这意味着——老板一周不开一次页面，这件事就等于没做；现算的结果也不落库，
今天看到的和明天看到的是两次临时计算，没法对比，也没法回看「上周二它就该提醒我什么」。

这一版把这件事从「页面功能」改成「系统行为」：

```
每天 8:00（可配）
   ↓ 调度器线程自己醒过来
   ↓ 扫一遍：待审批 / 该回访的客户 / 在跑的项目 / 真实毛利
   ↓
   ↓ 算出今天的待办，写进 daily_briefs 表
   ↓
   ├─→ 事件总线发一条 brief.ready（页面开着就自己刷新）
   └─→ 配了 webhook 就推出去（企业微信机器人 / 飞书 / 自建服务都行）
   ↓
老板什么时候打开，看到的都是当天那一份；不打开，那份也已经在那儿了
```

**三个设计选择，都写在代码里**：

| 选择 | 为什么 |
| --- | --- |
| **不调模型** | 简报是照着库里已经有的事实算出来的（待审批、该回访、在跑的项目、真实毛利）。调模型只会让它说得像个人话，不会更准，还烧额度 |
| **同一天只有一份** | 当天重跑是覆盖，不堆历史噪音。SQLite 用 `INSERT ... ON CONFLICT` 保证两个实例同时跑也只写一条 |
| **推不出去不算失败** | webhook 挂了只记状态，简报照样落库、照样能在页面看。老板的待办不该因为一个推送通道坏了就消失 |

**补齐了一个真实缺口**：管理接口以前只认本机。演示时老板在另一台机器上打开，
什么都是 403。现在这版让「主动经营」这件事真的能被外部看到——`/brief` 优先返回当天落库那份，
并用 `source` 字段说清楚它是 `scheduler`（系统自己扫的）、`manual`（有人点了「现在扫一遍」）
还是 `live`（实时算的）。演示时这句话很值钱：**「这是它自己每天早上扫出来的，不是我打开页面才有。」**

**顺带补了两件小事**：

- 手动钉经验：`POST /api/company/{id}/memories`。系统自动学的覆盖不了全部——
  老板当面说的一句「这个客户就是不要官方腔」，是一次性的、只有人知道的。
- 交付物字段回填：`trimmed` / `appendix` 是 v0.4.x 才加的，老交付的快照里没有这两个键，
  对接方按契约取字段会缺。新增 `tools/refresh_demo_db.py` 把随包发出去的干净演示库
  刷新到当前口径（**不动单数 / 项目数 / 任务数 / 收入这些演示数字**，只补字段、重算分数）。

新增 `tools/briefcheck.py`：离线段十二条断言（表在、生成、落库、同一天覆盖不新增、
内容结构完整、历史能读、调度器状态齐、当天不重复生成、force 能重跑），
在线段验四个新端点。自检从十件套变十一件套。

**契约 2.1**：新增 `brief_history`、`brief_generate`、`brief_scheduler`、`brief_scheduler_run`
四个端点与 `memories_create`；`/brief` 多了 `generated_at` / `source` / `brief_date` / `persisted`；
`/api/meta` 的 `capabilities` 新增 `auto_brief` 与 `brief_hour`。

## 已知限制

- 事件流用 150ms 轮询 SQLite 落库（而非内存队列），牺牲一点实时性换取"断线可重放、重启不丢"。真上量时应换 Redis Stream / Kafka，接口保持 `seq` 语义不变。
- 旧版 run 按拓扑序串行执行；任务层已支持依赖图并行，两套执行器并存。
- SQLite 单写锁，适合演示与小队内部使用，不适合多租户并发。
- 页面改成「推送 + 兜底轮询」了，但推送是**进程内**总线：单进程够用，多进程/多机部署时各进程只知道自己发的事件，要换 Redis Pub/Sub 之类的外部总线（`/api/events` 的报文格式不用改）。
- 订单交付物取「内容撰写」角色的成品，策划过程与完整原稿放 `appendix`；文件包（ZIP/PDF）已支持下载，但包里只有文字与附录，暂不含配图/表格附件。
- 后台推进是「尽力而为 + 补位」：进程在任务执行中被杀，那一单会从断点重跑未完成的任务，已完成的不会重做；但没有分布式锁，多进程同时跑同一个库会抢任务。
- 对账只覆盖「已交付未入账」这一种缺口；收入记错金额、记到别的项目上，目前靠人看。
- 知识库分域只覆盖「下单执行的流程」：跑单引擎（`/api/runs`）没有订单上下文，仍按全库检索。
  命中率靠关键词，同义改写（「月饼」vs「糕点」）认不出来——换真正的向量模型才能解决。
- **跨任务记忆只覆盖「下单执行的流程」**：跟知识库分域一样，跑单引擎（`/api/runs`）没有订单上下文，
  取不到服务，因此不会带服务专属的记忆（通用记忆仍会带）。
- 记忆记的是**结构化的教训**，不记原文全文——记忆塞满提示词反而干扰写作。同一岗位同一服务最多留 8 条。
- **未配 Key 时交付物是「作业骨架」不是「市场结论」**：模拟器只引用你的真实输入、给取证方法和测算口径，具体数字要人去核实。要直接交付给客户，必须接真实模型（见上文「接入真实模型」，并用 `tools/llmcheck.py` 确认退出码为 0）。

## 安全边界（v0.3.1 加固）

默认配置是「本机演示」，不对外暴露管理能力。三层闸门各自独立：

**第一层：管理接口只认本机**

未设置 `SF_ADMIN_TOKEN` 时，管理类接口（组织、员工、项目、任务、审批、账本、订单列表）只允许回环地址访问，其他机器一律 `403`。买家侧接口不受影响：`/api/products`、`POST /api/orders`、`/api/pay/notify` 始终公开。

要在手机上打开管理台，设一个长随机串再启动：

```bash
SF_ADMIN_TOKEN=换成你的长随机串 python run.py    # Windows: set SF_ADMIN_TOKEN=... 
```

之后所有管理请求需带 `X-Admin-Token: <同一串>`（页面右上角填一次，存 cookie）。设了令牌后，本机访问同样要带令牌，不再有"本机免验"的后门。

反向代理场景才需要 `SF_TRUST_PROXY=1` 来信任 `X-Forwarded-For`。**别在没有可信代理时打开它**——客户端可以伪造这个头冒充 127.0.0.1。

**第二层：订单凭据**

下单成功返回 `access_key`（`ak_` + 32 位十六进制），买家链接形如 `/q/pay/{order_id}?k={access_key}`。查询他人订单时：不带凭据或凭据错误都返回 `403`，不泄露订单是否存在。凭据校验用 `hmac.compare_digest`，避免时序侧信道。历史订单（加凭据字段前创建的）启动时自动补发，不会出现"老订单永远打不开"。

**第三层：支付回调验签与幂等**

- 沙箱模式：必须同时匹配服务端签发的 `txn_id` 与该订单的 `access_key`，缺一即 `400`，不落账。
- 微信 V2：按字典序拼接参数 + 商户密钥做 MD5 校验，签名不符拒绝。
- 支付宝：未配置公钥时直接拒绝，不做"验不了就放行"。
- 幂等：回调可重复投递，账本 `income` 对 `ref_id` 建唯一索引，`sync_order` 用条件更新（`WHERE status != 'delivered'`）保证并发下只记一笔。实测 20 并发回调只产生 1 条收入。

**其他加固**

| 项 | 处理 |
| --- | --- |
| 成本计算 | 修掉运算符优先级错误（日薪 ÷ 8 的括号），成本不再虚高 8 倍 |
| 订单字段更新 | `UPDATE` 走白名单，未登记字段直接丢弃而不是拼进 SQL |
| 后台线程 | 执行线程收归受管线程池，不再裸 `daemon` 启停 |
| LLM 失败 | 不再静默降级成模拟结果，异常向上抛并在事件流留痕 |
| 取消订单 | 连带停止关联项目，不再出现"单取消、工还在跑" |
| 入参校验 | 日薪、预算拒绝负数；金额一律整数分 |
| 经营总览 | 查询次数从 98 次降到 7 次 |
| 业务异常 | `CompanyError` 统一映射为 4xx，不再整站 500 |
| 事件序号 | 走 `seq_counters` 计数表，不再每次 `MAX(seq)` 全表扫描 |
| 空目录首跑 | 启动前先建表+写种子，不再因 `no such table: kb_entries` 崩溃（发给别人的包解压即可跑） |

**上生产前必须补的三件事**（当前都不做，别直接对外网开放）

1. 反向代理 + HTTPS，管理台加登录会话（现在只有单令牌）。
2. 多租户隔离：SQLite 单写锁 + 全局知识库，撑不住并发与分权。
3. 真实退款与对账：目前只有 `refunded` 状态位。

## 继续开发时，文档怎么跟着改

**不是每次提交都要动三份文档。** 按你改了什么对号入座：

| 你改了什么 | README | 接口对接说明 | API.md | 演示台词 |
| --- | --- | --- | --- | --- |
| 内部实现：算法、SQL、性能、修 bug、质检阈值、重试策略 | 不用 | 不用 | 不用 | 不用 |
| 接口字段 / 端点 / 状态码 / 错误码 | 可选 | **必改**：`contract.py` 字段清单 + `CONTRACT_VERSION` 加一位 + 变更记录补一行 | **必改** | 不用，除非页面显示也变了 |
| 端口、依赖、启动方式、环境变量 | **必改** | **必改** | 改 Base URL | **必改**（台词里的网址） |
| 页面路径、步骤数、按钮名、自检分数、页面上的数字 | 不用 | 不用 | 不用 | **必改** |
| 发新版本（改 `APP_VERSION`） | **必改**：加一节 `vX.Y.Z` | 视情况 | 不用 | 不用 |

**演示台词最容易漏**：它写死了「九个步骤」「能照做 18/25」「62 分」「收 99」这类现场数字，页面一改就会念错。稿里已加一句「以现场页面为准」，但步骤数和按钮名仍然要同步。

**一条命令兜底**：

```
python tools/aligncheck.py
```

它会检查端口是否统一、文档里的端点是否还活着、新接口有没有收进 `API.md`、契约版本与应用版本有没有登记；有欠账就退出码 1。改完代码先跑它，比事后回忆可靠。
